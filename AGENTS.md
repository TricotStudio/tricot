# Tricot: rules for agents

Tricot is a shared planning board for people and coding agents: a Node server (REST, SSE, MCP), a React page, and the `tricot` command. Layout and long form: [CONTRIBUTING.md](CONTRIBUTING.md#how-the-code-is-laid-out).

## Layers

- The page must not import Node or server code: the web bundle runs in the browser. Pinned by `test/bundle.test.ts`. A block kind's, connector's or agent's Node part goes in its `server.ts`, which the web build leaves out.
- Node code in `src/` asks which system it runs on only through `isWindows` or `currentOs`, and takes home, temp folders and PATH lookups from `src/platform/`: tests can stand in another system there. The page and `hooks/*.mjs` check on their own.
- Start a program that can be a Windows `.cmd` (agents, npm, npx) with `runProgram` or `execProgram` from `src/platform/run.ts`: they quote it safely. The pty switcher, which refuses Windows, is the exception.
- Put updating Tricot in `src/install/`. The CLI must not take OS or updating code from `src/server/`, and `src/platform/` and `src/install/` import nothing from it; `src/core/routes.ts`, which they load, imports nothing but `src/core/route.ts`. Pinned by `test/layers.test.ts`.
- Features in `src/web/` import one another one way: `shared/` imports no feature, and a feature reaches another only through its `index.ts`. Pinned by `test/webImports.test.ts`. The canvas and the connectors are the one pair that may reach each other's files.
- The core and the canvas side must not import the code of a part that adds kinds of card: name a new store module or page feature on its side. What the canvas needs of a card of such a kind (what a pinned part becomes, where a comment on a card's canvas or the summary of a pairing session on it goes), it asks from the registry of card kinds (`src/core/store/cardKinds.ts`), which a part fills where the Store is built (`src/core/store.ts`): add to that registry rather than import a part's module. A card's page address (what the Slack share links to) is the kind's `pageLink`, asked with `store.cardLink`; the terminal's chat takes its kinds of card as `ChatCard`s (`src/cli/switcher/threadsSend.ts`) from `run.ts`, and with none it links and comments on no card.
- Tricot Canvas is a second entry point, a separate build and start, never a mode read at run time. The page: `src/web/canvasMain.tsx` and `canvasApp.tsx` build the registries with only the core's and share `page.tsx` and the shell with a page that registers parts; `vite build --mode canvas` writes `dist/canvas`, so a thing a part adds to the page must be registered from that part's own page entry, never imported by a core feature, or it reaches Canvas's bundle. The server: `canvasEdition()` in `src/server/canvasEdition.ts` is empty registries of API parts and tool groups and a plain Store with no part, so Canvas registers nothing of a part's: its Store reads and writes no list, dismissal or event subject a part adds, and its board JSON, board list and replies carry no list or count of one (a reader treats a missing list as empty), handed to `startServer` by `src/server/canvas.ts`. A board's data is the same file, and Canvas leaves what a part stored alone, row by row: a Canvas rename leaves a card's `boardId` at the earlier id, an alias the part resolves, and a Canvas delete leaves the board's dismissals in their own table. A part's style rules are not in the shared sheets: they are in sheets of the part's own, imported by its page entry after `styles.css` and never by Canvas's, so they still come after the shared rules they extend. Pinned by `test/canvasPage.test.ts`, `test/canvasServer.test.ts` and `test/canvasAgent.test.ts`.
- `tricot canvas` is the one `start` in `src/cli/boardCommands.ts` with `canvas` set, never a second copy of it: it gives `startServer` `canvasEdition()` and `dist/canvas`, through `await editionOf(canvas)` in `src/edition.ts` (the one file that chooses an edition: it looks for the edition file, `src/editionFull.ts` (which exports `fullEdition`, `fullSwitcher` and `fullTitle`), at that one fixed path and imports nothing else of it, so `tricot`, `tricot start` and `npm start` start that edition where the file is and Canvas where it is not, and `tricot canvas` and `npm run canvas` always start Canvas; the lookup takes no search path or setting, so it is not a plugin API, `editionTitle(canvas)` gives the running edition's display name (Canvas's, `CANVAS_TITLE`, is in `src/server/canvasEdition.ts`), and `start` follows the edition it got, so a tree without the file starts Canvas, with `dist/canvas` and `edition: 'canvas'` in its lock; `startServer` and `createApp` given none build a plain Store and serve the core alone), and the package ships `dist/canvas` with `dist/web` (`files` in `package.json`, checked by `scripts/smoke-release.mjs`), where `npm run build` (`scripts/build.mjs`) builds `dist/web` only where the page's own entry (`src/web/main.tsx`) is and the notices follow the bundles built (`buildsOf` in `scripts/notices.mjs`). Which Tricot holds a data folder is `edition` in the lock (`ServerLock`, set from `canvasEdition().edition`; none is the edition of `src/editionFull.ts`, as every older lock), which a start of the other one reads to refuse in a sentence naming the one that runs and `tricot stop`; the same `edition` is in the update's `ServerPlace`, so the restart after an update is `tricot canvas`, not `tricot start` (`startArgs`, `restartCommand` in `src/install/handoff.ts`). The agent commands start what `tricot` starts when none runs and use whichever runs. Pinned by `test/cliCanvas.test.ts`, and the restart by `test/handoff.test.ts` and `test/updates.test.ts`.

## Adding a thing

- Block kind: a folder in `src/core/blocks/` and `src/web/canvas/blocks/`, and a line in each `registry.ts`. Nothing else switches on a block's type, or on a pinned part's kind: a kind says how its parts read in `pins.parts`. Only the website kind (`site`) has more: its site server, in `src/server/sites/`. Check with `npx tsx scripts/check-new-kind.ts`. A kind only a part adds has its page half in that part's folder, registered with `useWebBlockKinds` (`src/web/canvas/blocks/registry.ts`) where the part's page entry starts, so the Canvas page has no such kind.
- Connector: a folder in `src/core/connectors/`, `src/server/connectors/` and `src/web/connectors/`, and a line in each `registry.ts`. Its REST routes go in `src/core/connectors/<id>/routes.ts`, which the connector registry gathers, and the links it recognises in `sources.ts` beside it, built on the service's plain link source when it has one. Nothing else names a service. Check with `npx tsx scripts/check-new-connector.ts`.
- Link source that needs no sign-in: a file in `src/core/sources/` and `src/web/canvas/sources/`, and a line in each `registry.ts`. Check with `npx tsx scripts/check-new-connector.ts`.
- Kind of reference (what `#12` and `T5` in text name): an entry in the page's registry of reference kinds (`src/web/shared/refKinds.ts`), made by the feature that owns the card and handed to `RefsProvider` where the board's page is built (`src/web/board/BoardView.tsx`). The shared Markdown, composers and links ask the registry and name no kind, and a page with none registered leaves `#12` and `T5` as text and offers no `#` list. The server and the terminal ask `src/core/refKinds.ts` the same way: it has no kind until a part (or the terminal's edition, `SwitcherEdition.refKinds`) registers some. Pinned by `test/refKinds.test.ts`, `test/refMarks.test.ts`.
- Kind of card, for what the canvas side of the page asks of a card by its id (where it is, what a pinned part becomes, how a reaction to its comments is sent, the chat bar's plain question, the cards an agent has claimed): an entry in the page's registry of card kinds (`src/web/shared/cardKinds.ts`), made by the feature that owns the card and handed to `CardKindsProvider` where the page is built. The canvas, the threads, the agents' panel and the connectors ask it with `useCardKinds` and name no route or address of a card, and a page with none registered offers no pin that becomes a card, leaves a card's link as text and lets a reaction on a card do nothing. What says those kinds' words is registered beside them, never written in the core: the pin menu's words (`wordPinsWith`, with its Ready now checkbox and the tooltips of a pinnable line and block), the agents' panel's (`wordAgentPanelWith`: what its Working on tab says and the activity rows that count cards), a kind's `workCard` (how a thread shows a card of it), `requestCardsWith` (the cards a request made) and the `question`'s `note`; with none, the words are plain ones that name no card. The board context's address is `linkTo.context`. Pinned by `test/webCardKinds.test.ts`.
- View of a board (a tab, a card's own page, a control in the header, the strip of what needs the viewer, the Feed, Home's list of needs): an entry in the page's registry of board views (`src/web/shared/boardViews.ts`), registered by the side that owns it and handed to `BoardViewsProvider` where the page is built (Canvas's is `canvasBoardViews` in `src/web/canvasApp.tsx`). The core registers the Sketchbook and the Files (`src/web/board/coreViews.tsx`); a part registers its own views, its cards' own pages, its header controls, the needs strip, the Feed and what Home draws of its cards (`HomeSlots`). `BoardView`, Home and the board switcher import no part's feature: they ask the registry, and a page built with only the core's views is a board of the Sketchbook and the Files, which lands on the Sketchbook (the registry's landing). What a side keeps for a board while it is open is its session, a hook it registers (`withSession`). The model of what is new since the viewer looked (`useAway`, `src/web/live/away.ts`) is the page's, for the Sketchbook's change dots and for a part's views alike. A part's wording is registered there too: its part of the search palette (`withSearch`), what the name gate says a name is for (`withWords`, plain words with none), and the line of the live label's card that says which cards an agent has in progress (`withAgentWork`). What a part draws on the board context's canvas, and what it is called, is one slot (`withBoardContext`, `BoardContextSlot`), which `CanvasView` asks only on the canvas of the board itself (no card, no page): with none registered that canvas draws no sync mark and no bar, and a result, a card or a file on it says only "the board" or names nothing. The slot also holds `keep`: its button's words, its call and the line that says where the blocks went, for a block's and a group's menu on a Sketchbook page, which `CanvasView` offers through the canvas context's `keep` and which `nodes.tsx` draws without naming it, so a Canvas page has no such item in either menu. An agent's card (`T5`) is said only where the card kinds have work an agent claims (`useAgentOn`). Pinned by `test/boardViews.test.ts`.
- Share of a card through a connector (a card's ⋯ menu sending it to a service the person signed in to, as Share to Slack does): it is a part's, never the connector's. The page's half is a `ConnectorShare` the part registers with `useConnectorShares` (`src/web/connectors/registry.ts`) from its own page entry, by the connector's id, so a page with none (Canvas's) has no menu item and no dialog in its bundle; the dialog's styles are the part's own. The route is in the part's own table, under the connector's address (`/api/connectors/<id>/…`), served by its API part, which reaches the connector through `kit.connectors` (`ApiKit`) and asks `personOnly` for its tier: the connectors' router leaves a path it does not serve to the API router, which answers the 404 where no part serves it. The connector keeps only its sign-in, its reading and what it already offers (`call`).
- Agent: a folder in `src/core/agents/` (`index.ts` for the page, `server.ts` for the rest) and a line in its `registry.ts`. Code that handles every agent reads the registry, not a list of its own. An agent whose session makes a folder also goes in the sweep list in `src/cli/agentSessions/folder.ts`. Check with `npx tsx scripts/check-new-agent.ts`.
- Board MCP tool: one `defineTool` entry in its area's file in `src/server/mcp/tools/`, a row in `docs/mcp-tools.md` and a step label in `hooks/tricot-describe.mjs`. `test/mcpTools.test.ts` fails for a tool registered twice or missing its row or its label. A connector's tools go in its `src/server/connectors/<id>/tools.ts`.
- Group of MCP tools, with the guide topics it adds: a `ToolGroup` in the registry each MCP server is built with (`src/server/mcp/toolGroups.ts`, `McpOptions.groups`, `toolGroups` in `createApp`), which a part fills with its tools. A group says which board tool its tools follow (`after`) and what it answers of a board tool's call that carries an argument it added (`answers`, over the generic `CommitFiles.lookup` where it reads where an area lives), and `read_guide` offers the topics of what is registered, so a server with none lists none of a part's tools and answers a call to one as any unknown tool. Nothing registers by loading a module. Pinned by `test/toolGroups.test.ts`.
- Step labels of a part's tools (how a live step names a call to one: "Using Tricot: …"): in a file of the part's own, `hooks/tricot-labels.json` (`tools`, a label for each tool, and `cards`, the arguments that name one of the part's cards and the step field each goes on as), never in `hooks/tricot-describe.mjs`, which names only the board's own tools and the connectors'. The package ships the file where the part is; the live-steps installers (`src/server/hooks/`) copy it beside the hook when the package has it (`hasLabels`, `LABELS_FILE`) and take it out with the rest, and nothing names a part. The hook reads it if it is there and goes on without it if it is absent or broken: a part's tool then reads as any other. The server, which ends the step the hook sent for a write and so must say its words as the hook does, takes the same words from the part's `ToolGroup` (`stepLabels`, which the part fills from that one file), never from the file beside the hook, which a bundled server is not beside. Pinned by `test/mcpTools.test.ts`, `test/toolGroups.test.ts` and `test/connectAll.test.ts`.
- Line of the MCP instructions: a named line of `CORE` in `src/server/mcp/instructions.ts` when it is true with no part registered, and otherwise a line a `ToolGroup` adds with `instructions` (a group may list no tools and only add lines). A group's line names where it goes among the core's lines (`before`, `after`, `replaces`, or `in` a section) and never edits the text of one. A server with no group opens with the core's short neutral line and names no tool or word of a part; with a part registered every variant reads exactly as it did, and each stays under `MAX_INSTRUCTIONS`. A line that a canvas alone and a part say differently has the core's version in `CORE` and the part's, which replaces it, in its own file. Pinned by `test/instructions.test.ts` and the golden `test/golden/mcp-instructions-canvas.txt`.
- Words of the board's own tools, guide and refusals that name a part's cards, status or board context: named pieces the core writes (`[name, text]`, in `src/server/mcp/words.ts`, `describedIn` for an argument) with a part's placed among them by a `ToolGroup`'s `phrasing` (`edits`, `params`, `lines`, and for a digest `parts` and `offers`). A group says a piece `before`, `after` or in place of a piece of the core's, and never edits the text of one; the arguments that take a card and the board context (`board_id` on `get_canvas`, `add_block` and `add_group`, where the core asks for `page_id`) are a part's to add, not the core's, and a tool that is only for the board context is a part's own tool. A digest the core builds (`boardDigest`, `canvasDigest`, a session's updates, `requestsDigest`, the thread digests, `boardListDigest`, `searchDigest`) takes what a part says of the board from `told` (`Told` in `src/core/words.ts`): a `part` of a digest, a `line` made for the call, pieces among a text (`say`), what the group `offers` and which kinds of event it tells (`events`, `tells`, `src/core/eventsTold.ts`). With none it names no card, status, board context or sync, lists no request that asks for one, leaves out the comments, pins and events of a part's cards, and tells no event of a part's kind: the log is the part's data and stays as it is. A server with a part registered says every description, argument, topic and refusal exactly as it did, so a new sentence in a board tool that names a card, the board context or a part's tool is written in pieces with the part's words in its phrasing. Pinned by `test/canvasAgent.test.ts`, `test/words.test.ts` and `test/canvasResults.test.ts`.
- CLI command: one entry in `COMMANDS` in `src/cli/commands.ts`, with its own options and help. Pinned by `test/cliCommands.test.ts`.
- REST route: one entry in `routes` in `src/core/routes.ts`. The server registers it with `routesOn`; the page calls it through `src/web/shared/api.ts` or `routeUrl` (the shared client holds the canvas's calls and the core's, and names no route of a part: a part's feature, like a connector, has an `api.ts` in its folder built on `get` and `post`), and the command, `src/platform/` and `src/install/` through `routeUrl`. None writes an `/api` path by hand: a signed request signs that same address. Pinned by `test/routes.test.ts`. A connector's go in its `src/core/connectors/<id>/routes.ts`. A part's routes go in a table of its own that imports nothing but `src/core/route.ts` and that nothing in the core or the canvas side imports: its API part declares it. The core's table holds none of a part's routes.
- REST handlers of a part besides core: in an API part (`src/server/apiParts.ts`: an id and a `mount(api, kit)`), never in `src/server/api.ts`, which holds the core's. `createApiRouter` mounts the parts `createApp` gives it after the `peopleChange` gate and before the 404 and the error handler, so a part's routes keep the gate, their tiers and the shared error handler: never mount a part's own router at `/api` beside it. Register each route with the kit's `on` and take `seated`, `personOnly`, `human`, `param` and `react` from the kit; a part that keeps what a person answered to an agent waiting for their OK (`src/server/approvals.ts`) subscribes with the kit's `onApprovalAnswered(listener)` while it mounts, and a listener that throws is logged and never holds the answer back. Each app builds its own parts, handed to `createApp`; `new ApiParts()`, what `createApp` has when given none, is the canvas alone, which answers a part's route with the plain 404; nothing registers by loading a module. A part declares its routes as a table of its own (`routes` on the part), serves each of them and no other, and a part that serves one outside it or leaves one unserved stops startup. `GET /api/needs` is the core's route (the boards in use with their work and the agents around them, for Home and the board switcher); a part adds what waits on the person through its `needs` source, and a server with none answers that nothing waits on anyone. `GET /api/info` lists the ids of the parts (`parts`: `[]` for the canvas alone), so a client tells Canvas from a fuller edition before it asks; the field is added to what the board says and the protocol did not change with it. Pinned by `test/apiParts.test.ts`.
- Page address: one entry in `src/core/pages.ts` for a page of the core's (Home, the Connectors page, a board's own address, the Sketchbook's pages, the Files, a pin), and one in a table of the part's own for a page of a part, whose pieces the part registers as the `address` of the view or card page that draws it. A board's address is `#/b/<id>` and then a piece that the core or a registered view reads, and one no piece reads is the board's own, which lands on the registry's default view. The page links with `linkTo` and goes with `go`, and never writes a `#/` address by hand. A page's older addresses are not kept (no redirects): change an address and its old form opens the board's own. Pinned by `test/pages.test.ts`.
- Web code: in its feature's folder in `src/web/`, shared pieces in `src/web/shared/`. `styles.css` lists its sections in cascade order: add a section where it applies.
- Styles: draw with the theme tokens; never style for one theme. Pinned by `test/themes.test.ts`. A rule for a piece only a part draws goes in a sheet of that part's own, never in a shared sheet, which Canvas builds.

## Data

- Adding a block kind, or a value of an enum a board stores, must add a migration in `src/core/store/migrations.ts`: an older Tricot then refuses the data instead of failing on it. Pinned by `test/dataShape.test.ts` (the core's own types, `test/dataShape.core.json`). [More](RELEASING.md).
- The check for which picture files are still in use (`Assets.removeUnusedAssets`, run when a page, a board or a lapsed deletion lets a picture go) reads the stored rows as well as the boards in memory: every `block` and `deletion` row of every board and owner (`src/core/store/pictureRows.ts`) and the `block_versions` table's asset column, whichever lists the store has registered. A picture only a part's card's canvas shows keeps its file in a store that does not read those rows, and deleting a board removes the pictures its unread rows showed once nothing else shows them. It never rewrites a row, and a row it cannot read keeps the pictures its text names. A new row kind or table that can name a picture is read there. Pinned by `test/storePictures.test.ts`. Every id the repository makes (`newPageId`, `newItemId`, `newThreadId`, `newRequestId`) and any id a part makes is checked against the ids of the rows the store does not read, and a new generator must check them too. [More](CONTRIBUTING.md#the-data-a-tricot-stores).
- Never edit a migration that has shipped, `src/core/store/shapeDefaults.ts` included: add a new one.
- A part besides core versions its own data: its migrations are a `DataPart` in `src/core/store/dataParts.ts`, the `data` of its `StorePart`, each migration naming the core data version it was written on (`core`), and its version is its row in `data_versions`. Add one at the end of its list. Core's version stays `user_version`, and core never names a part. A Store opens the database with the data parts of its own parts and no others (`addDataPart`'s process-wide list is read only by a Store given no `parts`), and a part whose data the file holds in a newer version is switched off for that Store: its lists, owners and kinds of card are not registered, its rows stay foreign, and the Store says so once. A Store with no part, such as Canvas's, neither writes nor touches a part's row. Pinned by `test/dataParts.test.ts`. [More](RELEASING.md).
- The store reads and writes only the rows of the lists it has registered (`src/core/store/entityLists.ts`): a list is its name on the Board, its row kind and the owner kind its canvas rows use. Pages, threads, requests, deletions and a canvas's blocks, groups, links and pins are the core's own; a part's lists are registered by the part, and a Store given no parts has none. `boardRows.ts`, `boardTables.ts`, `boardDb.ts` and `repository.ts` ask the registry for the lists, their dirty tracking, their indexes and what a row is, and a new list is an entry there, never a name in them. With none registered (`lists: []`) every other row is foreign: never parsed, compared, rewritten or indexed, deleted only with its whole board, with its owner, kind and id kept so no new id is made twice, and a board header keeps the keys it has no name for, in their order. Stored data does not change with the registry: no migration, and the data tests below stay as they are. [More](CONTRIBUTING.md#the-data-a-tricot-stores).
- A Store is built from parts (`src/core/store/storePart.ts`): `new Store(dir, { parts })`, where a `StorePart` is a name and what it gives the Store, its entity lists, its canvas owners, its kinds of card, its data parts, its tables keyed by board, the subjects events are about (read and written by), what counts towards a board's activity and how agents read its cards, each optional. `parts: []` and a plain `new Store(dir)` are a canvas alone. A part's `modules` builds what its `cards` work over from the Store's own (`CoreModules`), so the core Store imports no module of a part; a plain Store has `getCard(kind, id)` (the repository's `findCard`, `getCard` and `findCardById`, by the registered owners), and asks a kind by its name for what server code that Canvas also runs needs of a card (`commentOnKind`: the comment tool, which refuses in a sentence when no kind has `commentOn`; `sweepKinds` and `touchOnKind`: what runs out of time on a kind's cards and what an agent's call about one keeps). `composeParts` merges the parts in order and refuses a part name, list, row kind, owner, table, event subject or kind of card that two parts both have, naming the part that came second. A canvas owner is the kind of card that has a canvas of its own: `BoardRepository.locate` finds a canvas by a registered owner, and answers a ref to a card of an owner no part registered as it answers any card that is not on a board: not found. `refOf`, `ownedCard`, `isCardCanvas` and `guardSync` read a Located by its owner's key and name no owner. A table a part keeps by board (`tables` on the part: a `StoreTable` with a name, `build(db)` and a `removeBoard(key)` on what it builds, such as a table of dismissals) is built once for each connection by `BoardWriter`, which holds only the tables its Store's parts registered and calls each one's `removeBoard` when a board is deleted; the table is still made by a migration, never by `build`. `BoardDb.table(kind)` and `BoardRepository.table(kind)` reach one, and the module that owns it asks for it by its kind: the core's code names none. A Store whose parts did not register a table leaves its rows alone, a deleted board's included, and a part that is off has none of its tables registered. Events are read by a subject a part registers (`subjects` on the part: a name and the generated column of the `events` table that holds its id, and the core's own `item`): `EventTables` (`src/core/store/eventTables.ts`) builds its filters from the registry and names no column of a part's, and a query asks for a subject as its name and `Id`. A query naming a subject the Store did not register, which `parts: []` and a part that is off do not, is refused with a `BoardError`, never ignored. Events are written by the same subjects: `BoardRepository.record(board, actor, type, summary, about, options)` takes what the event is about by subject name (`about`, `item` the core's) and `at`, `mentions`, `commentId`, `forAgent` and `held` as `options`, and refuses an `about` that names a subject the Store did not register, so the core's own events (boards, pages, requests, threads) record with no part. A subject may also give `list`, the entity list its rows are in, which is the row a change about it saves (`dirtyBy` names no list), and `agent`, which agent an event about it is for when `forAgent` is not given: a new call site names its subject in `about`, never a column or a list. A pin's links come from stored data, so `recordCanvas` keeps only the subjects the Store registered (`EventRegistry.known`): a Store without them records the event about the item alone and never throws halfway through a change. A repository built with no registry has the core's `item` alone, as it has no lists. What counts towards a board's activity beyond the latest of each actor is a rule a part gives (`activity`: a name and a condition over the table's columns), so `activity()` holds no card-specific text. How agents read a card (who a backlog card is for besides those @-mentioned on it, and which events about a card concern an agent) is a `CardReading` that a part gives (`reading`, `src/core/cardReading.ts`, read by `core/concerns.ts`, `server/mcp/backlog.ts` and the terminal's who-line). It is the process's: set when a Store is built from a part that gives one, and by the terminal (`runSwitcher`, given its `SwitcherEdition`: chat cards, reading and board cards), which holds no Store; a Store whose parts give none leaves what was set. With none set, a backlog card is for the agents it @-mentions and no event about a card concerns an agent. A part may also give `boardCards` (what each kind of card says of its number, title, discussion and canvas to a reader that has only a board: `cardsOf`, `cardOf`, `findCard`, `linkedCard`, `eventCards` and `eventCardsLeading` in `src/core/cards.ts`, process-wide like the reading), and `header` (the keys it adds to a new board's header, which keep the stored text's order; a board of a Store without the part has none of them). A part may also give `activityStart`, the keys its activity notes keep, and `summary`, the keys it adds to a board's entry in the list of boards; a deleted card, a request's kind and a thread ref's kind are named by registered kinds (`DeletedCardKinds`, `RequestKinds`, `ThreadRefKinds` and `ReactionCards` in the core's types, which a part adds to). An activity rule may give a `note`, what its part makes of an event in a board's activity (`noteEvent` given no notes means the ones registered for the process by `useActivityNotes`, which the page does where its entry starts, so a caller with no Store at hand notes who acted alone). `CanvasOwners.links` and `linkTo` read and write a pin's `<owner>Id` links. Pins, canvases and the sentences of the log read a board's cards through them (`canvasesOf`, `pinTarget`, `where`, `canvasName`, `pinRef`): a kind's `named`, `statusWord`, `settled`, `options`, `reactionAbout` and `answerAsks` are what they ask beyond its number, title, discussion and canvas, and `namedCards`, `cardOwning` and `linkOf` read a link or an owner by its kind's key. The core's `types.ts` holds the core's types alone: a part adds its own by module augmentation, in a file of the part's own, so the core's `tsc` sees the core's alone. What `record` stores is pinned by `test/recordSubjects.test.ts`. A canvas owner may give `mark`, which `BoardRepository.deletedCard` writes a deleted card's line by (`src/core/deletedCards.ts`); an owner with none is not named once deleted. Search asks where a card stands (how it closed, which card replaced its answer) of the kinds registered in `src/core/searchCards.ts`, which a part registers when it is made (process-wide, as `searchBoards` reads boards with no Store): with none, no card is closed or replaced. Search also asks the kind for the words a card is found by, and walks the cards of `cardsOf(board)`, so a kind with no search card is still searched by its discussion and canvas. Home's work per project (`BoardWork`) comes from the `ProjectWork` an app gives `projectsAcross` as `work` (`src/core/projects.ts`; it is the app's, not the process's, and a Canvas server's projects carry neither `work` nor `needs`), and a working agent's card is its focus by `cardOf`, else what the part's `claimed` says. A test of the core that needs a card makes a kind up, never a real one (`test/madeUpCards.ts`: `cardPart`, `CardStore`, `seedCards`, `TICKETS`, `MEMOS`); `Store.repo`, `core`, `pins` and `cards` are protected for the Store a part adds methods to, and `BoardRepository.indexCard` and `unindexCard` index a card made while the Store runs. A kind of card may also say that a person can ask agents for it from a Sketchbook page (`asked`, a `CardAsk` from `src/core/askedCards.ts`: the request kind's name, its words and how an agent answers it), how tall it makes a group that shows it (`heights`), the event type recorded when one is made (`postedIn`) and how it keeps the thread it was made from (`setFromThread`, `createdBy`, `statusWords`); a request keeps the cards made for it as `<kind>Ids`, and `core/requests.ts`, `store/requests.ts`, `core/threads.ts` and `store/threads.ts` read all of it from the registry and name no card (a thread ref's `kind` is `block`, `comment` or a registered kind). The places that name a kind of card by its type take `CardKindName` (`keyof CardKindNames`, `src/core/pins.ts`), a search result's kind is `SearchKind` (`keyof SearchKinds`; `searchKinds()` lists the registered kinds of card, then the core's), and a thread's door is `ThreadDoor` (`keyof ThreadDoors`) whose words are registered with `useDoors` (`src/core/doors.ts`). The conversation's readers (`mentions`, `delivery`, `answering`, `reactions`, `chatStream`, `threadList`, `threadSelection`), the terminal's chat and the MCP server's readers find cards through the same registries: a kind may say who made it (`createdBy`), the heading an agent is told of it (`heading`), who is working on it (`workedBy`) and who follows it (`followedBy`), whether a card waits out of agents' reach (`backlog`), and an event's comment is found by `eventCardComment` in `src/core/conversationCards.ts`. The REST bodies that name a card (a canvas, a pin's target, an events query, a step) take the `<kind>Id` of a kind `store.cardKinds()` lists, and an events query reads any other parameter as a kind, which a Store that keeps no events about it refuses in a sentence. The card reading, the board cards, the search cards, the reference kinds, the door words (`useDoors`) and the terminal's chat fields (`useChatFields`) stay process-wide by design: each process runs one edition (a Canvas process loads no part, and the lock allows one edition per data folder), so they are always the right ones there, and a test that builds Stores of both editions in one process registers what it needs; Home's project work is the app's (`ProjectsOptions.work`). ## Security

- A route that acts as the person must check `asPerson` or `personOnly` in `src/server/access.ts`: other accounts on the computer can reach the port.
- The lock's secret goes only to `src/server/proof.ts` and the approval hook: never log, send or return it. `test/lock.test.ts` and `test/approvals.test.ts` check it never reaches commands, pages or replies.
- A connector in the core must not depend on a confidential secret: the code is public. Ship only what the service treats as public (a client ID, Google's Desktop client); otherwise sign in with PKCE, device flow or a token the person pastes.

## Tests

- The suite stays small and fast. Add a test only for stored data (a migration or a golden file), security, a contract at its edge (an agent tool, a REST route, or a registry these docs promise) or a smoke test of a page. Extend an existing test or golden before adding a file. Add no test file that drives Chrome.

## Systems and running things

- Code must work on macOS, Linux and Windows, or refuse with a message saying why. CI runs Linux and Windows; macOS is not in CI, so run the tests on a Mac yourself when a change touches what differs there (`src/platform/`, paths, processes, the pty switcher), and each release runs the whole suite on the Mac it is made on before it is tagged, and makes its Homebrew bottle there. A test that needs POSIX skips on Windows with its reason: `{ skip: WINDOWS && '…' }` from `test/platform.ts`.
- Run anything by hand on a scratch port and data folder (`PORT=4610 TRICOT_DATA_DIR=$(mktemp -d) npm start`): `~/.tricot` holds the person's own boards.
