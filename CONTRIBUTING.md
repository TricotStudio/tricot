# Contributing to Tricot

Thanks for helping. Two things first.

## The licence, and your contribution

Tricot's core and command line are open source under the [Apache License, Version 2.0](LICENSE). Every contribution also needs the [Contributor Licence Agreement](CLA.md): You keep your copyright and give the Licensor the right to relicense Your contribution, commercially included. Read it, then comment "I have read the CLA and I agree to it" on Your first pull request. A pull request without that can't be merged.

## Working on the code

The source is at https://github.com/TricotStudio/tricot. Fork it there and send changes as pull requests.

```sh
git clone https://github.com/TricotStudio/tricot.git
cd tricot
npm install
npm test            # store unit tests + MCP/REST end-to-end tests
npm run typecheck
npm run dev         # the board on http://127.0.0.1:4545: server + Vite HMR on one port, restarts on server changes
```

The suite stays small and fast on purpose. Add a test only for stored data (a migration or a golden file), security, a contract at its edge (an agent tool, a REST route, or a registry these docs promise) or a smoke test of a page. Extend an existing test or golden before adding a file. Don't add a test file that drives Chrome.

`npm start` runs the server with the built UI instead, so build it first:

```sh
npm run build
npm start           # http://127.0.0.1:4545
```

`npm run build` (`scripts/build.mjs`) builds Tricot Canvas into `dist/canvas` (`npm run build:canvas`) and then the command (`npm run build:cli`), whose notices cover the bundles built (`buildsOf` in `scripts/notices.mjs`). Where the page has an entry of its own beside Canvas's, `src/web/main.tsx`, it is built into `dist/web` first (`npm run build:web`); a tree without that entry removes any `dist/web` an earlier build left, and `vite build` there stops saying so. `npm run canvas` runs Tricot Canvas, the same server with only the core and the Canvas page, and `npm run canvas:dev` runs it with Vite as `npm run dev` does for the page.

Use a scratch port and data folder for anything you try by hand, so you don't touch your own boards:

```sh
PORT=4610 TRICOT_DATA_DIR=$(mktemp -d) npm start     # or npm run canvas
```

To see what the board's MCP tools cost agents, ask the running server: `curl http://127.0.0.1:4610/api/tool-costs`. It tallies every tool call since the server started, by tool and by agent: calls, and the average, largest and total size of what the agent sent and what it was answered, in tokens estimated at four characters each (`src/server/toolCosts.ts`). It keeps sizes only, never what was said.

To see the update notice without a release, start Tricot with `TRICOT_UPDATE_URL='data:application/json,{"version":"9.9.9"}'`: the check reads that instead of asking npm, even from a checkout.

Report a bug or suggest a change in the [issues](https://github.com/TricotStudio/tricot/issues). Open one before a large change, so we agree on the direction first.

## How the code is laid out

```
src/cli/           the `tricot` command (bundled with the server into dist/cli/command.js; bin.ts, the package's bin, checks the Node.js version first); commands.ts lists every command, one entry each
src/cli/switcher/  agents in a pseudo-terminal each, beside Tricot's own tab (chat, threads, your agents' status and requests for permission), with a strip at the bottom that switches between them (`tricot claude codex`); not on Windows
src/core/          domain model, store (all mutations + event log), agent-facing digests; routes.ts is the table of the core's and the canvas's REST routes the server serves and the page and the `tricot` command call (each connector's own are in its folder, gathered by the connector registry, and a part's are a table of its own), pages.ts the table of the core's pages and their addresses (Projects, the Connectors page, a board's own address, the board's Home and a thread open in it, the Sketchbook's pages, the Files and a pin; a part has a table of its own for its pages), ranks.ts the maths of placing a thing among others people arrange by hand (a page in the Sketchbook), refText.ts how a text names the cards on a board (#12, T5) for any kind of card that says how its numbers are written
src/core/store/    the Store's modules (core/store.ts hands each call to the one that owns it), the boards' SQLite file and event log under them, and migrations.ts, the versions of what a board stores (core's, and, in dataParts.ts, those of the parts besides core that version their own data)
src/core/schemas/  the one schema set: what people send (the REST bodies), what agents send (the MCP tools' arguments) and what the Store takes, written from the same fields and limits (a part's bodies are files of its own, which the others do not export)
src/platform/      what differs between macOS, Linux and Windows: home, temp and data folders, finding a program, running and stopping one, opening the browser, file privacy, the server's lock, and the token a program sends to a board that listens beyond this machine
src/install/       updating Tricot in place: the handoff to the new version, the update check, a release's file
src/server/        Express app: REST + SSE for the UI, MCP endpoint (one session per agent; mcp/session.ts, and the tools in mcp/tools/, one file per area); start.ts starts it with the edition it is given (canvasEdition.ts, or the one `src/edition.ts` finds in `src/editionFull.ts` where that file exists), for the command, `npm start`, `npm run dev` and Canvas's `npm run canvas` alike (runFromSource.ts; canvas.ts is Canvas's entry and canvasEdition.ts what Canvas leaves out of the server)
src/server/sites/  the site server: a second listener, on this computer alone, that serves each website block at an origin of its own, with Tricot's frame script in its pages
src/server/hooks/  the live-steps installers, one per agent (named in its server.ts): each copies what it needs of hooks/ into the agent's folder and adds its lines to the agent's settings
src/web/           React UI, in a folder for each feature: shell/ (what every page is shown in: its top bar, your menu, the tab's title, the toasts and dialogs), board/ (a board's page, and the Sketchbook's and the Files' views the core registers on it), live/ (a board's live data, what is new since the viewer looked, and the boards in use with the agents around them), threads/ (the chat bar, the threads panel, and a board's Home: its conversation, the yarn of its threads and Work), bell/ (Canvas's header bell: what needs the viewer on a board, and the switch of notifications), conversation/ (discussion, delivery, reactions), canvas/ (the whiteboard, React Flow), scratch/ (the Sketchbook: a board's pages, and the Pages button on a page's canvas), connectors/, agents/ (live steps, usage, the Live label, connecting an agent), access/ (seats, requests for permission), projects/ (Projects, the list of boards), update/, themes/, shared/ (the REST client, the page's addresses, hooks, components, the registries of reference kinds, of card kinds and of board views); canvasApp.tsx opens the page the address names in the shell (page.tsx) with the core's registries alone, from the entry canvasMain.tsx, which `npm run build:canvas` builds, and a page with parts has an entry and registries of its own, where a part registers what its features add; styles.css lists the page's shared styles (styles/) in the order they apply, and a feature's own styles sit beside its components
hooks/             what an agent runs or loads to send Tricot its steps, its permission prompts and its plan usage: the steps hook and the module that puts a step in words, Pi's, OMP's and OpenCode's extension and plugin, the approval hook, the prompt hook with the lenses and the showing words it reads ("show me … on Tricot"), the usage script
scripts/           the check-new-* scripts prove what adding a kind, a connector or an agent takes; the build, brand and release helpers
docs/              the guides the README links to: the command, how Tricot works, the MCP tools, configuration
test/              what `npm test` runs, a file per area; fixtures/ holds a database saved by each release
brand/             the mark's files and icons, made from the app's own mark by `npm run brand` (brand/README.md says which is for what)
packaging/         the Homebrew formula, written at each release (RELEASING.md)
```

Node code in `src/` asks `src/platform/` which system it runs on, and nothing else in `src/` reads `process.platform` (the page reads the browser's `navigator`, and the hooks, which run on their own, read it themselves). `isWindows`, and the functions that default to `currentOs()` (`home`, `which`, `launchOf`, `openCommand`), take a stand-in system, so tests check the Windows paths on any machine. A program that can be a Windows `.cmd` (agents, npm, npx) is started with `runProgram` or `execProgram` (`src/platform/run.ts`), which start a `.cmd` through `cmd.exe` with each word quoted so nothing in it runs as a command; the pty switcher, which refuses Windows, starts its helpers itself. `src/platform/` and `src/install/` sit under the server and the command, and import nothing from `src/server/`: what they share with the server lives down there, and the server re-exports it (`test/layers.test.ts`). A test that needs a POSIX shell, file modes, signals or a terminal skips on Windows with its reason: `{ skip: WINDOWS && '…' }` from `test/platform.ts`.

A board's MCP tool is one `defineTool` entry in its area's file in `src/server/mcp/tools/`, with a row in `docs/mcp-tools.md` and a step label in `hooks/tricot-describe.mjs` (`wait_for_updates` and `get_updates` have none on purpose); `test/mcpTools.test.ts` fails for a tool registered twice or missing its row. A connector's tools are `ConnectorTool` entries in its own `src/server/connectors/<id>/tools.ts`. A part's tools (the ones besides the board's own) are not in the board's own list: a part registers them as groups of tools (`ToolGroup` in `src/server/mcp/toolGroups.ts`), the edition gives `createApp` those, and with none given it serves the board's own tools alone (`toolGroups`, handed on in `McpOptions.groups` as `connectors` is). A group has its tools, which each session builds as it builds an area's, the guide topics it adds with what each covers, the board tool its tools follow in the list an agent gets, and the calls of a board tool it answers when they carry an argument it added (`answers`, the board's own handler answering the rest, and the generic `CommitFiles.lookup` reading where an area lives), so the list and the parts of each guide topic read in the order they always did. Each server has its own registry, because nothing is registered by loading a module. `read_guide` offers and takes the topics of what is registered, the core's (`canvas`, `blocks`, `conversation`) and the groups', so a server with no group lists none of a part's tools, offers no topic for them, and answers a call to one of them as it answers any tool that does not exist. A group whose tools cannot be built is left out of that session with its topics, and the server says why once in its output; a second group of one id, a topic the core or another group already has, a tool named as another is and a group that follows a tool the board does not have are mistakes in Tricot, and each is refused with its name. Only the tools and what they say move: the handlers of the board's own tools that take a card (`get_board`, `search`, `comment`, `react`, `pin`, the update and wait tools, the thread and request tools) still handle them, and the labels of a part's tools are the part's own: a file `hooks/tricot-labels.json` (`tools`, a label for each tool, and `cards`, the arguments that name one of the part's cards and the step field each goes on as) that the live-steps installers (`src/server/hooks/`) copy beside `hooks/tricot-describe.mjs` where the package has it (`hasLabels`, `LABELS_FILE`) and take out with the rest, naming no part, which the hook reads if it is there and goes on without when it is absent or broken (a part's tool then reads as any other), and which a part's `ToolGroup` gives the server as `stepLabels`, as the server says a step's words as the hook does to end it; a part's tools have their rows in the part's own tools doc, not in `docs/mcp-tools.md`, which lists the board's own tools. `test/toolGroups.test.ts` holds the order of the list and the answer to a tool nobody registered. A `tricot` command is one entry in `COMMANDS` in `src/cli/commands.ts`, with its own options and help; dispatch, both kinds of help and "did you mean" read it, and the agent commands come from the agent registry. A command that needs something the board started serving (a route, a tool, a command or option the board hands agents) raises `PROTOCOL` in `src/core/protocol.ts` and says `needsBoard` in its entry, so an older board is refused in a sentence naming `tricot update` rather than failing on what it lacks; the board says its protocol at `GET /api/info`, and `src/cli/boardVersion.ts` checks it.

The instructions every agent is told on connecting are composed from named lines (`src/server/mcp/instructions.ts`), not written as one text. The core's lines are the ones that are true with no part registered: a short neutral line it opens with, the line that says how the session idles (`wait`: the sleeping line for a session Tricot's terminal wakes or that sleeps by `tricot listen`, and the listening line for any other), how to find the board, how mentions and threads work, and how to write to people. A `ToolGroup` adds lines with `instructions`, each naming one position: `before` or `after` a line of the core's, `replaces` one, or `in` a section, at its end. Lines at one position keep the order the groups were added in, and a group never changes the text of a core line. A part's lines may be one group of their own that lists no tools, because they are one story across its tools: its role replaces the neutral line, and its other lines sit where they sat when the text was one string, so with the part registered an agent is told exactly what it was. A line that the core and a part word differently, such as the one about what people point at an agent, has the core's version in the core and the part's, which replaces it, in the part's file. A group whose `instructions` throw is left out of that session and the server says why once in its output; a position that is no line of the core's, a line with no position or with two, a line named as another is, and two groups replacing one line are mistakes in Tricot, and each is refused with the group's name when the instructions are built. The text of each variant stays under `MAX_INSTRUCTIONS` (3,800 characters) whatever registry a server is built with, so a word added anywhere in it is paid for there. `test/instructions.test.ts` holds this against a golden file in `test/golden/` that carries the text in full: `mcp-instructions-canvas.txt` is the canvas alone, and moves when the core's own lines do (`npx tsx test/instructionsSurface.ts --write canvas`).

The board's own tools say nothing of a part's cards, and a part's words are placed among theirs as its instruction lines are. The core writes a description, a guide text or an argument's description (`describedIn`) that a part has words for as named pieces, `[name, text]`, joined exactly as written, so a piece carries its own spaces and one may be empty to name a place (`src/server/mcp/words.ts`). A `ToolGroup` gives `phrasing`: `edits`, by the id of a text (`<tool>.description`, `<tool>.guide`, `<tool>.<argument>`, `topic.<name>`, or a sentence a tool says as it refuses, such as `comment.on` and `connector.ask`, or a line of advice or a connector's summary, such as `advice.raw-id` and `connector.linear.tools`), each a piece that goes `before` or `after` a piece of the core's or `replaces` it, inside a sentence as well as between two; `params`, the arguments it adds to a board tool at a position among the core's, or in place of one (the arguments that take a card and the board context's `board_id` on the canvas tools are a part's, not the core's, which ask for `page_id`); and `lines`, a sentence made for the call at hand (the answer to a request that asks for a card); `parts`, a part of a digest the core leaves out, which a digest asks of `told` (`Told` in `src/core/words.ts`, which `Phrases` implements: a `part` of a digest, a `line` made for the call, pieces among a text with `say`, and which kinds of event it tells with `events` and `tells`, `src/core/eventsTold.ts`), for every digest the core builds (`boardDigest`, `canvasDigest`, a session's updates, `requestsDigest`, the thread digests, `boardListDigest`, `searchDigest`), so with none a digest names no card, status, board context or sync, lists no request that asks for one, leaves out the comments, pins and events of a part's cards, and tells no event of a part's kind, while the log keeps them as they are; and `offers`, what it gives agents that the core does not (`board-context`), which says whether a request asked on the board context is named at all and whether `take_request` takes one. The tool a session lists has them composed (`wordedBy` in `src/server/mcp/tool.ts`), so a server with a part registered says every description, argument, guide topic and refusal exactly as it did, and one with no group says only the core's. A group whose phrasing throws is left out of that session and the server says why once in its output; a piece named as another is, a position that is none or more than one, a piece of the core's that is none, two groups replacing one piece and arguments for a tool the board does not have are mistakes in Tricot, and each is refused with the group's name. A connector's tool takes the same words for its description and its refusals (`ConnectorTool.run` is handed what says them, and `src/server/connectors/ask.ts` is how each ends a refusal). Where a sentence has a part's words in the middle of a clause, the core's piece is cut at them and the part's goes between the halves or stands in for a short piece, so the core's text is a sentence of its own, not the part's with words missing; `test/canvasAgent.test.ts` holds what a Canvas server lists and tells to the core's alone, and `test/words.test.ts` holds the composition.

A REST route is one entry in `src/core/routes.ts`: its method and its path, with `:name` where a value goes. The server registers it from that entry (`routesOn` in `src/server/routing.ts`, whose handlers are Express's own) and the page builds its address from it (`get(routes.x)` and `post(routes.x)` in `src/web/shared/api.ts`, which fill the values in and encode them; the client there holds the canvas's calls and the core's and names no route of a part, and a feature that has calls of its own keeps them in an `api.ts` in its folder, built on the same `get` and `post`, as each connector does), as the `tricot` command and `src/platform/` do with `routeUrl(routes.x, …)` (a signed request signs that same address), so there is no path to write twice. A connector's own routes are a table in its core folder, `src/core/connectors/<id>/routes.ts`, written with the same helpers (`src/core/route.ts`) and listed on its kind; its server and web halves import that table, and `connectorRoutes()` in `src/core/connectors/registry.ts` gathers every connector's, so the app's table names no service. A part's routes are a table of the same kind of its own, and the app's table holds none of them: the part's API part declares it, its page features import it, and nothing in the core or the canvas side does. `src/core/routes.ts` and a part's table import nothing but those helpers, because the platform and the command's small modules load the first and the page's features the second (`test/layers.test.ts`). `test/routes.test.ts` fails for a route served without an entry in one of the tables, or a call the page, the command or the platform makes to an `/api` address no table holds.

The core's REST handlers are `createApiRouter` in `src/server/api.ts`; the handlers of a part besides the core are an API part. A part (`src/server/apiParts.ts`) is an id, its table of routes and a `mount(api, kit)`. `createApiRouter` mounts each part it is given just before its 404 and error handler, which is after the gate that asks a person for every change (`peopleChange`), so a part's routes are gated, keep the tiers they ask for and meet the same error handler as the core's. A router of the part's own mounted at `/api` would be gated wrongly and miss that error handler, and a part mounted after the 404 would never be reached. The kit hands a part what the handlers use without importing the core's router: the store, the presence, `on` (which registers a route from an entry of a table, as the core does with `routesOn`, and records it), the tier middleware (`seated`, `personOnly`), and the `human`, `param` and `react` helpers. A part that keeps what a person answered to an agent waiting for their OK (`src/server/approvals.ts`) subscribes with the kit's `onApprovalAnswered(listener)` while it mounts; a listener that throws is logged and never holds the answer back. A part that throws while it mounts, registers a route that is already served, serves a route its own table does not hold or leaves one of its table unserved, stops the server from starting and names itself, and a registry refuses a second part of one id. `createApp` builds its parts for each app and, unless it is given its own (`parts`), has none, which is `new ApiParts()`, the canvas alone, which serves every route but a part's and answers one of those with the plain 404 of any route it doesn't have. Nothing registers by loading a module. A part declares its routes as a table of its own, as a connector does (`routes` on the part), and the bodies its routes take are schemas of its own, which the core's schemas do not export and only its API part imports. `GET /api/needs` is the core's route, which serves the projects and the agents (`src/core/projects.ts`) for Projects and the board switcher, and answers that nothing waits on anyone; a part with a `needs` source adds the rows, the total and each project's count, and a registry refuses a second source. `GET /api/info` carries `parts`, the ids of the parts the server has (`[]` for the canvas alone), so a client tells Canvas from a fuller edition before it asks for a route of a part's; `partsOf` in `src/core/protocol.ts` reads it, and a board older than the field says none, which is not the same as having no parts. The field is added to what the board says: a command that does not know it reads everything else as before, and `PROTOCOL` did not change with it. `test/apiParts.test.ts` holds the canvas alone, and the gate a part's routes keep, to this.

A page's address is one entry in `src/core/pages.ts`: the pattern of its addresses, what the page reads from one, and the link to it. The page opens what the address names with `useRoute` and builds every link with `linkTo` (`src/web/shared/pages.ts`), and the server and the command build their links to a page from it too, so a link and the page it opens can't drift apart; `test/pages.test.ts` fails on an address written by hand in the page.

The features in `src/web/` import one another one way. `shared/` imports no feature; a feature reaches another only through that one's `index.ts`, the list of what it lets the others use, never a file inside it; and no features reach each other, however far round. `test/webImports.test.ts` reads every import in the page and names any that breaks this. The one pair that reach into each other's files are the canvas and the connectors: a connector draws on the canvas, and the canvas finds the connectors through their registry.

The canvas side of the store and the page must not import the code of a part that adds kinds of card, so such a part can plug into the core instead of editing it. What the canvas needs of a card, it asks from the registry of card kinds, `src/core/store/cardKinds.ts`. A kind has an id and gives the canvas two things, each optional: `fromPin`, which makes its card from a pinned part, and `discussionOn`, which gives the discussion of the card whose canvas it is, where a comment on a part of that canvas goes and where the summary of a pairing session on it goes; a kind may also say where its card's page is (`pageLink`, asked with `store.cardLink`: the Slack share's link back), how a comment on one of its cards by id is made (`commentOn`, asked with `store.commentOnKind`: the comment tool names the kind by the `<kind>_id` it was given, and the kind says how the reply names the card), and what runs out of time on its cards and what an agent's call about one keeps (`sweep` and `touch`, asked with `store.sweepKinds` and `store.touchOnKind`). The terminal's chat is not a Store, so it takes its kinds of card as `ChatCard`s (`src/cli/switcher/threadsSend.ts`: a page address, and the routes a comment and a reaction go by), which `run.ts` takes from the edition it is given; a chat given none sends and links no card. A part's kinds are registered where the Store builds its modules (`src/core/store.ts`), unless it is given other parts (`new Store(dir, { parts })`; the registry is one object of the part, see [the data a Tricot stores](#the-data-a-tricot-stores)). Unlike the registries of block kinds, connectors and agents, each Store has its own, because a kind is made of that Store's modules, working over its repository. A Store with none registered is the canvas alone: pins and comments work on a Sketchbook page and the board context, and turning a pinned part into a card, or commenting on a part of a card's canvas, is refused in a sentence (a `BoardError`) that says this Tricot has no such cards. A kind makes its card before anything on the canvas changes, so what it refuses leaves no card and no pin, and a comment its discussion can't take leaves no part pinned for it; if what a kind still does once the pin is there (`afterPin`) fails, the card and its pin both stay. Ending a pairing session never needs a card: with no kind registered for its canvas, or a discussion that throws on the summary, the session ends with its line in the activity instead of a comment, and the error is not the person's to meet.

The page's text follows the same rule. The shared Markdown, composers and links name no kind of card: what `#12` and `T5` in text link to, and what typing `#` in a composer offers, come from the registry of reference kinds, `src/web/shared/refKinds.ts`. A kind has an id, the marks its numbers are written with (`T` and `#T`, and `#`; the first labels a card), and, for the board on screen, what each number is: the card it names and how the page draws it (its title, its status in words, the class of its status marker, its address and what opening it does), or who deleted it. `src/core/refText.ts` finds the references in a text from those marks and marks them up in rendered Markdown, and knows no kind itself. The server and the command ask `src/core/refKinds.ts` instead, which lists the kinds a process reads and labels cards by (none until it is given some with `useRefKinds`, which a part and the terminal's edition do; none finds no reference and labels no card; `refMarks.ts` is the list the page's registry extends). The `#` list is one registration beside the kinds, a picker, because it offers the cards of every kind in one order. A part's kinds and picker are registered by the part, and the board's page registers them where it builds what every view of a board gives its components (`BoardView`, the `kinds` it hands `RefsProvider`). Unlike the registries of block kinds, connectors and agents, this one is the page's own: nothing is registered by loading a module, so a test, or another Tricot, builds the kinds it wants. A page with none registered is the canvas alone: `#12` and `T5` stay text, typing `#` offers nothing, and nothing throws. Only cards are named in text today, so a kind for anything else is one more entry. `test/refKinds.test.ts` and `test/refMarks.test.ts` hold the registry to this.

The canvas side of the page asks for what it needs of a card by its id in the same way, from the registry of card kinds, `src/web/shared/cardKinds.ts`, which mirrors the Store's. A kind has an id and gives the page up to six things, each optional: `byId`, where a card is (its address, and what opening it does), from its board's id and its own; `pin`, the button the pin menu offers for it on a canvas, with how it makes its card from the part pinned; `react`, how a reaction to a comment on a card of this kind is sent; `question`, the plain question the chat bar posts while no agent listens, and the comment that follows it; `work`, the cards an agent has claimed, for its panel; and `workCard`, how a thread shows a card of this kind under the reply that made it. The pin menu's words, which say what its buttons do together (and its Ready now checkbox, and what a pinnable line or block says it can be pinned to), the agents' panel's words (what its Working on tab says with nothing claimed, the activity rows that count cards) and how the cards a request made look in their group are one registration each beside the kinds (`wordPinsWith`, `wordAgentPanelWith`, `requestCardsWith`), as the `#` list is, never words written in the core; the plain question's `note` is its own. An agent's card (`T5`) is said only where the card kinds have work an agent claims (`useAgentOn`). A part registers its kinds and those words, the page entry builds them and hands them to `CardKindsProvider`, a feature of the canvas side reads them with `useCardKinds`, and a link to a card is a `CardAnchor`, which becomes plain text where no kind says where the card is. The registry of reference kinds answers by number, for what a text names, and this one by id, which is all the canvas side holds (an agent's panel has only a board's id), so the two stay apart. A page with none registered is the canvas alone: a pinned part can only be commented on, a pinned card's chip and an agent's answer say what they are and open nothing, a reaction on a card's comment can't be added, an agent's panel has no Working on tab and no row that counts cards, a thread shows nothing under a reply for a card, a request's cards are not drawn, a card can't be shared to Slack, and the chat bar on a card's own page starts a thread. A kind that refuses what it is asked is told where it was asked, in the pin menu, under a reaction, in the bar and in the agent's panel, and nothing else changes. A reaction on a thread or a pin is the page's own call (`api.reactInThread`, `api.reactOnPin`), and a card's goes through its kind. The board context's address is `linkTo.context`, so the canvas side names no page of a part for it. `test/webCardKinds.test.ts` holds the registry to this.

A board's page is composed from a third registry of the same kind, the views of a board (`src/web/shared/boardViews.ts`), so `BoardView`, Projects and the board switcher import no part's feature. A view has an id (what a thread stores as its door), a tab (its label, where it leads and its count and dot from the board and what is new), the door the chat bar over it opens, and what it draws; a card's own page says which card its address names and draws it; and the registry has one slot each for the header's controls, the strip of what needs the viewer, the Feed, the search palette's part (`withSearch`), the wording of the name gate (`withWords`; plain words with none), what the live label's card says an agent is working on (`withAgentWork`), what a part draws on the board context's canvas and calls it (`withBoardContext`, a `BoardContextSlot`, which `CanvasView` asks only on the board's own canvas: each block's sync and owner marks, the Sync this and Sync group buttons, the selection bar, and the name of the board context in a result, a thread's card, a file's place and the General thread's note; the canvas of a card or a page, and any page with none registered, has none of it and says "the board" where a card or file sits on the board's own canvas; the same slot's `keep` is Keep in context, in a block's and a group's menu on a Sketchbook page, with its words, its call and the line that says where the blocks went, which `CanvasView` offers through the canvas context's `keep` and `nodes.tsx` draws without naming it, so a page with none registered, such as Canvas's, has no such item and shows no line), what Projects draws of a part's cards (the needs, the headline, each project's tag and column of work, the first run), what a part's cards add to the Work of a board's Home (`withWork`, a `WorkSlot`: its rows and the groups they stand in, placed among the core's Needs you, In progress, To do and Done; with none, Work lists the threads agents own alone), the kinds of reference a text can name, and the side's session (a hook the page calls in every render, for the state its views share). The core registers the board's Home, the Sketchbook and the Files in `src/web/board/coreViews.tsx`; a part registers the rest where its page entry is built. Each page builds its own registry where it is built (handed to `BoardViewsProvider`) and nothing registers by loading a module or from what the server says, so another entry builds the core's alone (`canvasBoardViews` in `src/web/canvasApp.tsx`, which adds the bell to the header). The default view is a property of the registry: a page may register one as the landing (the board's own address lands on it), and with none registered the first tab is, the board's Home; no page claims one today, so boards land on their Home. The model of what is new since the viewer looked (`useAway` in `src/web/live/away.ts`) stays the page's, as the Sketchbook's change dots and a part's views use it alike. With only the core's views a board shows its Home, the Sketchbook and the Files and nothing more, and an address of a part's page opens the landing. A board's address is its id and then a piece, and the registry is where the pieces come from. The core reads four itself (`src/core/pages.ts`): a page of the Sketchbook, the board's Home with the thread open in it, the Files with the file shown and whether it is paired on, and a pin. A view or a card's page registers the rest as its `address`, each a pattern of what follows `#/b/<id>`, with what it reads of it, and `pageAt` is given them (`useRoute` takes them from the registry), so a page built without a part reads none of its addresses and opens the board's own address for one: it lands on the registry's default view. A route says the view it opens (`view`, none for the board's own address and a pin's) and what a piece read (`piece`), which what registered it reads back by name. Every address a part's pages have is built from its own table and gone to with its own helpers, and the older forms of an address are not kept (no redirects). `test/boardViews.test.ts` holds the registry and `test/pages.test.ts` the tables to this.

A board's Home (`src/web/threads/timeline.tsx`, the core's view `timeline`, at `/home`) is the board's conversation: what people ask from the chat bar and what the coordinator answers, gathered from the threads that are not handed-out work and drawn as a thread draws its messages (`MessageRow` in `threads.tsx`), with a card under each ask that was sent on, or whose own thread an agent took on. Its yarn (`yarn.tsx`) is drawn beside it: the conversation is one strand plied from the mark's two yarns, and each thread an agent owns knits off it where it was sent on, in the colour of where its work stands (the `--status-*` tokens of `styles/base.css`, which a part's cards read too: at work is in progress, waiting on a person is in review, not started is to do), and is tied off when it is done; it is drawn from where the rows are laid out, and is only a quicker way to what the rows and Work say. Work (`timelineWork.tsx`) lists the threads agents own and what a part adds; pointing at a row lights its thread's strand. Pointing at a strand names it; clicking one opens its thread. The keyboard reaches the strands through a listbox over the yarn (← → between them, Enter opens one). The threads list opens from the ball of yarn at the top of the yarn (`YarnBall`), not from a button in the bar: the strands that run on past the top unwind from it (`Unwound`, drawn over the scroller from where `Yarn` says each lane runs, so it stays as the conversation scrolls). The threads' icon everywhere else, the bar's threads button included, is that ball drawn small (`thread` in `src/web/shared/components.tsx`). A thread opened, from its strand, a card or a row in Work, takes the main pane at its own address (`linkTo.thread`), with the one bar aimed at it by the bar's context chip (`ChatBar`'s `context`, as selected blocks use it), whose ✕ goes back to the conversation, as a click on the conversation's strand beside the thread does (the yarn's `onBack`). Whatever the bar is aimed at, it sends as the docked panel does (`send.ts`). The view says `holdsChat`, so the board's page draws no floating bar or docked panel over it, and it answers what asks the dock to open a thread (`useThreadsOpenHere`). It stores nothing of its own: it reads the threads, their status and the agents' steps and plans as they are.

Every kind of canvas block (note, table, chart…) is a folder on each side: `src/core/blocks/<type>/` says what it is (`index.ts`: its name, size, how it is placed and shown, and how the parts of it people pin read and behave, in `pins.parts`; `server.ts`: making and changing it, the text agents read, search, pins, what REST and MCP take, which the web build leaves out) and `src/web/canvas/blocks/<type>/` how it is drawn and added. A kind is registered with an import and an entry in `src/core/blocks/registry.ts` and `src/web/canvas/blocks/registry.ts`, and nothing else switches on a block's type or on a pinned part's kind; `npx tsx scripts/check-new-kind.ts` adds a throwaway kind that way and checks it end to end. Only the website kind (`site`) has more: the site server, `src/server/sites/`, which serves each website at an origin of its own so its scripts never run at Tricot's. The kinds are internal to the repository: there is no plugin API. A kind can belong to a part: the page that has the part adds its page half with `useWebBlockKinds` where it starts, and the Canvas page has no such kind. Its core half is in no `registry.ts` either: the part's `StorePart` gives it as `blockKinds` and the Store registers it for the process when it is built (`useBlockKinds`; the part's page does the same where it starts), a kind says where it sits in each listing with `follows` and that only a card's canvas takes it with `cardOnly` (the owner that takes it lists it in `takes`), and a Store without the part reads a stored block of its type as an unknown block (`kindOf`, `src/core/blocks/foreign.ts`): kept as it is, told to agents by its type, renamed and removed, and made or changed by none. The schemas that people's REST bodies are made from are built when their modules load, before a part's Store registers its kinds, so a block a part adds is checked as it is sent, and takes no field in a person's change or pin (`useBlockKinds` refuses a kind that does). A canvas is a card's through `CanvasView`'s `owner` (a kind and the card, with the `evidence` its blocks can be pinned to), never a prop for one kind of card.

A connector (Google, Figma, GitHub, Slack and Linear) is a folder on each of three sides: `src/core/connectors/<id>/` (who it is, the scopes it asks for in plain words, the links it recognises in `sources.ts`, how pins on its content are found, its REST routes in `routes.ts`; its `server.ts`, left out of the web build, holds what agents are told and its part of the store), `src/server/connectors/<id>/` (signing in, the sign-in kept in the data folder, reading and writing its documents, serving its REST routes and its MCP tools) and `src/web/connectors/<id>/` (its panel on the Connectors page, its marks, and its pieces on the canvas, such as Google's doc editor). The contract is `connector.ts` in each of the three, and each side's `registry.ts` lists the connectors with an import and an entry; the sign-in callback the Origin check lets through, the connectors line `list_boards` shows, the tools in `tools/list` and the links a card recognises all come from the registries, and nothing else names a service. A source of links that needs no sign-in (Figma, YouTube, Loom, GitHub) is smaller still: a recogniser in `src/core/sources/<name>.ts` and its mark in `src/web/canvas/sources/<name>.tsx`, with an import and an entry in each of their two registries. A connector for a service that has one builds on it: Figma's and GitHub's read a link with the plain source and add what they need once signed in (the file or the pull request to look up, and a card to show it on), and their sources are tried first. `npx tsx scripts/check-new-connector.ts` adds a throwaway connector and a throwaway source of links that way, checks them end to end (`test/routes.test.ts` among the checks), and takes them out. Connectors are internal to the repository too: there is no plugin API. The code is public, so a connector must not depend on a confidential secret: only what the service treats as public ships (a client ID, Google's Desktop client and its Picker key), and a service that wants a real secret is signed in to with PKCE, device flow or a token the person pastes.

Sharing a card through a connector (a card's ⋯ menu sending it to a service the person signed in to, as Share to Slack does) is a part's, never the connector's. The page's half is a `ConnectorShare` that the part registers with `useConnectorShares` (`src/web/connectors/registry.ts`) from its own page entry, by the connector's id, so a page with none, Canvas's, has no menu item and no dialog in its bundle; the dialog's styles are the part's own. The route is in the part's own table, under the connector's address (`/api/connectors/<id>/…`), served by its API part, which reaches the connector through `kit.connectors` (`ApiKit`) and asks `personOnly` for its tier. The connectors' router leaves a path it does not serve to the API router, which answers the plain 404 where no part serves it. The connector keeps only its sign-in, its reading and what it already offers (`call`).

An agent (Claude Code, Codex, Pi, OMP, Gemini CLI, OpenCode, Goose, Hermes Agent, Grok Build, Copilot CLI) is a folder, `src/core/agents/<id>/`: `index.ts` says who it is and what the page shows of it (its names, the command that joins it to a board or the file to edit, the Connect panel's words, what its usage shares, how to install it on each system, the models and thinking levels it can start on) and `server.ts`, which the web build leaves out, holds what only the command and the server use (how it starts for one session and its own flags for a model and thinking level, its live-steps hook installer, the skill `tricot connect` adds to it when it has skills (a `skill` line: its skills folder and its way to reconnect its tools), what `tricot connect` prints, the name its MCP client gives and how long that client lets one call run, which caps how long a wait for updates lasts). It is registered with an import and an entry in `src/core/agents/registry.ts`, and nothing else names an agent: `tricot <agent>` and `tricot connect`, their help, the Connect panel, first run, usage, the live-steps installers and the MCP server's waits all read that list. An installer or a session that needs files of its own can be a file in `src/server/hooks/` or `src/cli/agentSessions/` that `server.ts` imports, or be written inside `server.ts`. `npx tsx scripts/check-new-agent.ts` adds a throwaway agent that way, checks it end to end, and takes it out.

A theme is a CSS file of colour tokens in `src/web/themes/<id>.css` and a line in `src/web/themes/registry.ts`: its id, its label in the theme menu, and whether it is light or dark underneath (what the canvas, Mermaid diagrams and the browser's own controls are told). The file defines every token `light.css` does, under `:root[data-theme='<id>']`, with the `color-scheme` of its base; components draw with the tokens and none is written for one theme, which `test/themes.test.ts` checks. The menu lists what is registered, and the build writes the ids into the script that applies the theme before first paint. Following the OS shows the light or the dark theme; choosing any other one sticks.

What covers what on the page is one order, the layers in `src/web/styles/base.css` (`--z-floating`, `--z-cover`, `--z-docked`, `--z-popover`, `--z-panel`, `--z-dialog`, `--z-toast`, `--z-gate`, `--z-menu`, `--z-drag`, bottom to top). A z-index that sets where a piece sits on the page names one of them; a number from 0 to 9 orders pieces inside one part and never decides what covers what across the page, which `test/themes.test.ts` checks. A menu or popover drawn inside a container can never rise above that container's own layer, whatever its z-index, so one that must rise above what holds it (a block, the thread dock, a row) is drawn at the page's root with `OnTop` and placed by what opened it with `usePlace` (`src/web/shared/onTop.tsx`); a press in it counts as a press inside what opened it (`insideOf`, which `useDismiss` asks).

### Tricot Canvas

Tricot Canvas is a second entry point to the same code, with no part's features: a separate build of the page and a separate start of the server, not a mode either reads at run time, so nothing of a part's is in what runs, and tests hold that. The page is `src/web/canvasMain.tsx` and `src/web/canvasApp.tsx`: they build the registries the page asks of (card kinds, board views) with only the core's, from `coreBoardViews` alone, and open `page.tsx` in the shell, as a page with parts does with the registries of a part. The core's registrations are the board's Home, the Sketchbook and the Files, landing on its Home, and a header control, the bell (`src/web/bell/needsBell.tsx`), which counts what is new for the viewer on the board (the threads that wait on them and the agents waiting for their OK, which stay until handled, and the comments that @-mention them or reply to one of theirs since they last looked), opens each where it is answered, and holds the switch of the chime and desktop notifications (`src/web/shared/notifications.ts`), off until switched on and kept on the browser, which rings for the same things while the tab is in the background. Projects draws its plain form where no slot is registered (`ProjectsSlots` in `src/web/shared/boardViews.ts`): a headline of its own, and each project as its title, its description, the agents on it and when it changed. `vite build --mode canvas` swaps the entry script in the same `index.html` (`vite.config.ts`) and writes `dist/canvas`; its libraries are recorded as a bundle of their own for the third-party notices, as `dist/web`'s are (`scripts/notices.mjs`). A part's style rules are in sheets of its own, which its page entry imports after `styles.css`; Canvas's entry does not, so its build has none of them, and they still come after the shared rules they extend. `test/bundle.test.ts` holds both entries to holding no server code, and `test/canvasPage.test.ts` shows Canvas's Projects and board in a browser.

The server is built from the same pieces with nothing of a part's given: `canvasEdition()` (`src/server/canvasEdition.ts`) returns empty registries of API parts and of tool groups, and no Store part, so its Store is a plain `new Store(dir)` that registers nothing of a part's. `startServer` takes them as `parts`, `toolGroups` and `storeParts` and `src/server/canvas.ts` starts it with the Canvas page's folder, as `npm run canvas` does. The result lists the board's own MCP tools, which leave out the tools a part adds, and the core's short neutral instructions, `GET /api/info` says `parts: []`, a route of a part's answers the plain 404, and the board JSON, the list of boards and the replies carry no list of a part's cards and no per-status counts (a reader treats a missing list as empty). A board's data is the same file: what a part stored stays in it. `test/canvasServer.test.ts` starts the entry, and `test/canvasAgent.test.ts` reads what an agent is told: the board's 26 tools, the core's short neutral instructions, a canvas tool's schema (the core's block types alone) and the connectors' tools with their refusals, and holds them to the core's alone. `test/canvasResults.test.ts` reads the status event the log keeps and Canvas does not tell. A board's cards and log are not changed by Canvas, an agent is not told the events of a part's kinds that the log keeps, and a search does not return a card.

`tricot canvas` starts Canvas from an install: the command's `start` (`src/cli/boardCommands.ts`) with `canvas` set, which serves `dist/canvas` (shipped in the package beside `dist/web`) and hands `startServer` `canvasEdition()` (through `editionOf` in `src/edition.ts`, which hands the edition of `src/editionFull.ts` (it exports `fullEdition`, `fullSwitcher` and `fullTitle`) where that file is, and Canvas's own where it is not; `editionTitle(canvas)` gives the running edition's display name, and Canvas's, `CANVAS_TITLE`, is in `src/server/canvasEdition.ts`), so it takes `tricot`'s options and data folder, and `tricot status` and `tricot stop` find it. `start` follows the edition it got, so a tree without `src/editionFull.ts` starts Canvas from `tricot` and `tricot start` too, with `dist/canvas` and `edition: 'canvas'` in its lock, and `startServer` and `createApp` given no edition build a plain Store and serve the core alone. The agent commands start what `tricot` starts when none runs, and use whichever runs. `canvasEdition()` also says `edition: 'canvas'`, which `startServer` writes in the lock (`edition` in `ServerLock`; a lock without it is not Canvas's) and in the update's `ServerPlace`. A start of the other edition on a folder reads the lock and refuses, naming the edition that runs and `tricot stop`, and an update restarts the same edition (`startArgs` and `restartCommand` in `src/install/handoff.ts` say `canvas` or `start`). `scripts/smoke-release.mjs` starts the packed Canvas and checks its page, `parts: []`, the 404 and the refusal; a package without `dist/web` holds Canvas alone, and it checks the plain `tricot` and `tricot canvas` as Canvas, with its page in Chrome. `test/cliCanvas.test.ts` pins the command, `test/handoff.test.ts` and `test/updates.test.ts` the restart.

### The data a Tricot stores

A part's cards are not tables of their own: they are rows of the generic `items` table (a row kind each, and the rows owned by `<owner>:<id>`), the generated columns of `events` for the subjects the part registers with their indexes, a table keyed by board where the part keeps one, and a few keys of a board's header. The core does not name them in its code and types while the stored data does not change, so two things pin what it stores. `test/golden/data-schema-and-rows.txt` holds the schema of a new data file and a digest of each table of the databases the releases left (`test/fixtures/`) after the migrations; `test/dataGolden.test.ts` compares it, and it was written once and is never regenerated, so a change that makes it fail has to be fixed in the code and not in the file. `test/foreignRows.ts` reads a data file without any part's code and returns the rows the core does not own, in a form two files can be compared by, so a test can show that opening, changing and saving a file in Canvas left every one of them as the migrations alone made it.

Picture files are deleted when nothing shows them, and a backup holds only the database, so a file deleted while a row still names it is lost for good. `Assets.removeUnusedAssets` (`src/core/store/assets.ts`) is called when a page, a card or a board is deleted and when a deletion of earlier versions lapses (`pruneDeleted`). It first asks the boards in memory and the `block_versions` table (its `asset` column has an index), and for a picture still unused it makes one last pass over the stored rows (`src/core/store/pictureRows.ts`): every `items` row of kind `block` or `deletion`, on every board, whoever owns it, so a card's canvas counts in a store that does not read those rows. Each row's text is searched for names shaped like a picture's (twelve letters and an extension) and only a row that holds one of the pictures asked about is parsed, through the block kinds' own `assets`, so a note that only mentions a file name shows nothing; a row that cannot be parsed keeps the pictures its text names, since the other mistake cannot be undone. Rows are never written. Deleting a board reads its own rows the same way, so the pictures its unread cards showed go with it unless another board or version shows them. The pass is one scan of the table whatever the number of pictures: on a data file of 10,000 blocks and 60 cards it took about 8 ms for one picture and about 13 ms for 500, and reading a board's rows to delete it about 19 ms (`node:sqlite`, Node 22 on a laptop; a few thousand rows is a few milliseconds). A store with those lists registered finds the same rows in memory, so its behaviour does not change. In a Store with no list, `test/storePictures.test.ts` keeps a picture a row names whose body cannot be read, and looks for more pictures than one pass holds. Every generator in `repository.ts` is also checked against the ids of rows it does not read, with a forced draw for each; no test holds that now.

Which rows the store reads is a registry of entity lists (`src/core/store/entityLists.ts`): each entry names a list of a board, the kind of its rows in `items` and the owner kind of the rows on its cards' canvases (so `<owner>:<id>`). A part registers its entries (below). The Sketchbook's pages are the core's one list of that shape, and the threads, requests and deletions its plain ones, so a registry with no entry still reads all of them. `BoardImage`, `joinBoard`, `readBoards`, `BoardDb` and the repository take the registry and have none when none is passed. A row of `items` is read only if its owner is the empty one, `board`, or the owner of a registered or page canvas, with a kind that sits there; every other row is foreign to that store. A foreign row is never parsed, compared or rewritten, and the board image keeps only its owner, kind and id, which the repository holds as taken so that a new page, block, group, link, pin, thread or request never gets one of them. The only thing that deletes a foreign row is deleting its whole board, which removes the rows of it in every table the Store has registered, as it always did. A board header is the board without its registered lists, so the keys of the lists left out, and the others the core has no name for, stay as they were read, in their order. The core's `Board` type has none of a part's lists (a part adds them by module augmentation), and a store with them unregistered holds none (a list that says `always` is held empty by a Store of its part opening such a board), and renaming a board there does not rewrite a card's `boardId` (an owner that gives `holdsBoardId` has its cards' kept right).

A Store is built from parts, `new Store(dir, { parts })` (`src/core/store/storePart.ts`). A `StorePart` is a name and what it gives the Store, each optional: `lists`, its entity lists; `owners`, its canvas owners; `cards`, its kinds of card (`cardKinds.ts`), made over the modules its `modules` builds from the Store's own (`CoreModules`; the Store's own when it gives none), so the core Store imports no module of a part; `blockKinds`, its kinds of block; `data`, its data version and migrations (a `DataPart` of `dataParts.ts`); `tables`, the tables it keeps keyed by board; `subjects` and `activity`, how events are read and counted; `reading`, how agents read its cards; and `boardCards`, `header`, `activityStart` and `summary` (all below). A plain Store has `getCard(kind, id)` (the repository's `findCard`, `getCard` and `findCardById`, by the registered owners), and server code that Canvas also runs asks a kind by its name for what it needs of a card: `commentOnKind` for the comment tool, which refuses in a sentence when no kind has `commentOn`, and `sweepKinds` and `touchOnKind` for what runs out of time on a kind's cards and what an agent's call about one keeps. A part may give its lists and owners without its kinds of card, which is what a Store that still has to read its rows takes. `parts: []` is a canvas alone, and Canvas's Store is a plain `new Store(dir)`: it reads and writes none of a part's lists, the pictures and the ids stay closed (above), a part's tables are registered by the part and its events' subjects are the part's own, so a part's rows stay in the file for the next Tricot that has the part to open. `composeParts` merges the parts in order, so the lists, owners and kinds of card come in the order the parts are given, and it refuses a part name, list, row kind, owner, table, event subject or kind of card that two parts both have, with the name of the part that came second, and a data part name that two parts both have; a list needs its owner in the same part, and an owner its list. The older options `cards` and `lists` stay on `StoreOptions`: each replaces its half of the part a Store means by default, and giving them with `parts` is refused.

The tables a part keeps by board are part of the part. A `StoreTable` is a name, `build(db)` over the database and a `removeBoard(key)` on what it builds, and `composeParts` refuses a name two parts both give. `BoardWriter` (`src/core/store/boardTables.ts`) holds only the tables its Store's parts registered, builds each once for a connection (so two Stores in one process keep their own) and calls each one's `removeBoard` in the transaction that deletes a board. A part's table is registered by that part alone; the module that owns it reaches it by its kind, through `BoardDb.table(kind)` or `BoardRepository.table(kind)`, and neither the writer, `BoardDb` nor the repository names it. A table is still made by a migration, not by `build`, so no data changes. A Store whose parts did not register a table never builds it and leaves its rows as the file holds them, a deleted board's too, and a part found off does not register its tables either. A Store with no such table reads none and refuses to write one.

The events are read by subjects a part registers. The events table has a generated column for the id of what an event is about (the shipped migration makes one column for each subject and `item_id`), and a part's `subjects` name them: `{ name, column }`. The core's own is `item`. `composeParts` merges them in order, refuses a name two parts both give (or the core's), and `without` drops a part's. `EventTables` builds its filters from the registry: `EventQuery` takes a subject as its name and `Id` (`itemId`, and a part's), and a query that names a subject the Store has not registered is refused with a `BoardError` ("This Tricot keeps no events about …", naming the subject), so a canvas alone never answers a question about a card with every event. A part also gives `activity`, rules for the events that count towards a board's activity beyond the latest of each actor: a name and a condition over the table's columns, so `activity()` holds no card-specific text. `BoardActivity` starts with the keys a part's `activityStart` gives, which only a Store with the part has, and the events' own keys for a part's subjects are the part's types, written by the subjects' names in the order of the names. The REST route that lists events takes a part's subjects as parameters and the edge passes them as `<name>Id`; it reads any other parameter as a kind, which a Store that keeps no events about it refuses in a sentence. The MCP tools take none.

Writing an event goes by the same subjects: `record(board, actor, type, summary, about, options)`, where `about` names what the event is about by subject and `options` holds `at`, `mentions`, `commentId`, `forAgent` and `held`. A subject may give `list`, the entity list its rows are in, so a change that names it marks that row to be saved with no list named in the repository (`dirtyBy` names none), and `agent`, which agent an event about it is for when `forAgent` is not given (`null` is every agent). A part registers both for each subject it adds. A Store whose parts registered no such subject refuses an `about` that names one with a `BoardError`, and the core's own events name `item` or nothing, so they record with no part at all. `recordCanvas` takes a pin's links from stored data, so it keeps only the subjects the Store registered (`EventRegistry.known`) and the event is about the item alone in a Store without them. A `BoardRepository` built without a registry has the core's `item` alone, as it has no lists. What is stored does not change: the event body keeps its keys in the order `seq`, `at`, `actor`, `type`, a part's subject keys, `itemId`, `summary`, then `mentions`, `commentId`, `forAgent`, `held`. `test/recordSubjects.test.ts` does the same over the core's own events and a made-up kind of card, against `test/recordSubjects.digest.txt`, made on the code as it stood when events took their subjects. A canvas owner may also give `mark`, the label a deleted card's line is written with (`BoardRepository.deletedCard`, `src/core/deletedCards.ts`); an owner with none is not named once deleted, and search reads where a card stands from `src/core/searchCards.ts`, where a part registers its kinds (closed, replaced). Three more seams serve the readers that remain in the core: a part's `boardCards` say what each of its kinds of card is to a reader that has only a board (`cardsOf`, `cardOf`, `findCard`, `linkedCard`, `eventCards` and `eventCardsLeading` in `src/core/cards.ts`, registered for the process by the Store, the page and the terminal, never by loading a module), a part's `header` adds keys to a new board's header by position (`createBoard`; the stored text keeps its order, and a Store without the part writes none of them), a part's `summary` adds keys to a board's entry in the list of boards, and an activity rule's `note` is its part's reducer over a board's activity (`noteEvent` given no notes uses the ones registered for the process with `useActivityNotes`, which the page does where its entry starts, so a caller with no Store at hand notes who acted alone). A deleted card, a request's kind, a thread ref's kind and a reaction's card are named by registered kinds (`DeletedCardKinds`, `RequestKinds`, `ThreadRefKinds` and `ReactionCards` in the core's types, which a part adds to); a thread ref's `kind` is `block`, `comment` or a registered kind. `CanvasOwners.links` and `linkTo` read and write a pin's `<owner>Id` links, and pins, canvases and the log's sentences (`canvasesOf`, `pinTarget`, `where`, `canvasName`, `pinRef`) read a board's cards through `cards.ts` (`namedCards`, `cardOwning`, `linkOf`, and a kind's `named`, `statusWord`, `settled`, `options`, `reactionAbout`, `answerAsks`). A kind of card may also say that a person can ask agents for it from a Sketchbook page (`asked`: a `CardAsk`, `src/core/askedCards.ts`), how tall it makes a group (`heights`), the event type recorded when one is made (`postedIn`) and how it keeps the thread it came from (`setFromThread`, `createdBy`, `statusWords`), so `core/requests.ts` and `core/threads.ts` and their store modules name no kind of card; a request keeps its cards as `<kind>Ids`. The places that name a kind of card by its type take `CardKindName` (`keyof CardKindNames`, `src/core/pins.ts`), a search result's kind is `SearchKind` (`keyof SearchKinds`; `searchKinds()` lists the registered kinds of card, then the core's), and a thread's door is `ThreadDoor` (`keyof ThreadDoors`), whose words are registered with `useDoors` (`src/core/doors.ts`). Search, Projects and the page's readers use them: search walks `cardsOf(board)` and asks the kind registered in `searchCards.ts` for the words a card and its parts are found by (a part registers its search cards when it is made, process-wide, as `searchBoards` reads boards with no Store; with none, no card is closed or replaced, and a kind with no search card is still searched by its discussion and canvas), the per-project work on Projects (`BoardWork`) is the `ProjectWork` an app gives `projectsAcross` as `work` in `projects.ts` (it is the app's, not the process's, and a Canvas server's projects carry no `work` and no `needs`; a working agent's card is its focus by `cardOf`, else what the part's `claimed` says), and the page's Files places, "since you were away" and agent activity read a card or an event's card from `cardsOf`, `cardOf` and `eventCards`. The conversation's readers (`mentions`, `delivery`, `answering`, `reactions`, `chatStream`, `threadList`, `threadSelection`) find cards through them: a kind may also say who made it (`createdBy`), the heading an agent is told of it (`heading`), who is working on it (`workedBy`) and who follows it (`followedBy`), an event's comment is found by `eventCardComment` in `src/core/conversationCards.ts`, and `Where` in `delivery.ts` holds a card under its kind's name through `WhereCards`. The terminal's chat (`chatAim`, `threadsTab`, `threadsWho`) and the MCP server's readers (`mcp/backlog.ts`, `session.ts`, `tools/canvas.ts`, `tools/comments.ts`, `connectors/github/blocks.ts`) find cards the same way: a kind's `backlog` says whether a card waits out of agents' reach, `canvasDigest` takes the card that holds a canvas as one argument, and a board with no list of cards reads as having none. The card reading, the board cards, the search cards, the reference kinds, the door words (`useDoors`) and the terminal's chat fields (`useChatFields`) stay process-wide by design: each process runs one edition (a Canvas process loads no part, and the lock allows one edition per data folder), so they are always the right ones there, and a test that builds Stores of both editions in one process registers what it needs; the work per project on Projects is the app's (`ProjectsOptions.work`).

How agents read a card is a `CardReading` that a part gives (`reading`, `src/core/cardReading.ts`): who a backlog card is for besides the agents @-mentioned on it, and which events about a card concern an agent. `core/concerns.ts`, `server/mcp/backlog.ts` and the terminal's who-line read it. It is the process's: it is set when a Store is built from a part that gives one, and by the terminal (`runSwitcher`, given its `SwitcherEdition`: chat cards, reading and board cards), which holds no Store; a Store whose parts give none leaves what was set. With none set, a backlog card is for the agents it @-mentions and no event about a card concerns an agent.

A Store opens the database with the data parts of its own parts, so two Stores in one process keep to their own, and a Store built with `parts` never reads the process-wide list of `addDataPart`, which stays for a Store given no `parts`, which adds it to its own. When the database is opened and a part's data is found in a newer version than the part knows, the part is off for that Store: its lists, owners and kinds of card are not registered, so its rows are foreign and untouched, and the Store warns once (`composeParts(...).without`, `BoardDb.onPartsOff`). It stays off for that Store until it is built again. A part that a row of `data_versions` names and no registered part does is left alone and nothing is said. A part's data part is a baseline marker or its migrations at the version it knows, written on a core data version it names, and a Store of that part stamps it on any file it opens, after the usual copy of an existing one; a Store with no data part for it never writes or changes the row.

A canvas owner is the kind of card that has a canvas of its own: its name is the prefix of `<owner>:<id>`, the key of a `Located` and the start of a `CanvasRef`'s `<owner>Id`. `BoardRepository.locate` finds a canvas by the registered owner a ref names (a ref to a card is checked against the board it also names, where the owner's cards belong to one), then a Sketchbook page, then the board. With the owner unregistered a ref to its card is a card that is not found, as it was for a Store with no list. What reads a `Located` already made, `refOf`, `ownedCard` (which `recordCanvas` uses to mark the card as changed), `isCardCanvas` and the sync's guard, takes the card from the key that is not `board`, `canvas` or `page`, and names no owner. What still names a kind of card there: the schemas' `canvasBody` and `namesOneCanvas` (a REST body and an MCP tool name a card's canvas by the `<kind>Id` or `<kind>_id` of a kind the Store keeps, `store.cardKinds()`, so a Canvas Store reads no such key, and an id of a kind it keeps none of answers as a card not found; they reach the core through `canvasRef` in `src/server/mcp/tools/canvas.ts` and `locate`), `CanvasRef` and `Located`'s typed fields, the event columns `recordCanvas` and pairing fill, `where` and `label` in `labels.ts`, the message `locate` gives when no owner and no board is named, and what a part's modules do with their own cards. A test of the core that needs a card uses one of a made-up kind (`test/madeUpCards.ts`: `cardPart`, `CardStore`, `seedCards`, `TICKETS`, `MEMOS`), so it names no real card kind. `Store.repo`, `core`, `pins` and `cards` are protected for the Store a part adds methods to, and `BoardRepository.indexCard` and `unindexCard` index a card made while the Store runs. The core's `types.ts` holds the core's types alone: a part adds its own by module augmentation, in a file of its own, so the core's `tsc` sees the core's alone. Modules that read a part's lists by name (`canvasesOf`, `changes.ts`, `search.ts`) never see one, and an event about one is about its `item`.
