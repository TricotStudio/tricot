# Updates, configuration and Google sign-in

## Updates

Tricot's releases come from GitHub: each [release](https://github.com/TricotStudio/tricot/releases) carries the package as `tricot-<version>.tgz`, and npm and Homebrew get that same file. When it starts, and then once a day, the server asks GitHub for the latest release (`GET https://api.github.com/repos/TricotStudio/tricot/releases/latest`, which leaves out drafts and pre-releases). A release counts once its file is attached to it. That request is all it sends: no identifier, no sign-in, not the version you run, nothing about your boards; it says `tricot` as its User-Agent, because GitHub requires one. When GitHub can't be reached or turns the request down (offline, or its limit of 60 requests an hour from one address is used up), or its latest release doesn't have its file yet, the server asks the npm registry instead (`GET https://registry.npmjs.org/tricot/latest`). The answer, and which of the two gave it, is kept in memory and in `update-check.json` in the data folder, so a restart within the day doesn't ask again. Offline, the check gives up after five seconds, tries again an hour later, and never holds up the start.

When a newer version is out, Home and each board's top bar say so quietly ("Tricot 0.2.0 is out"), with the first paragraph of the release's notes (the part before its install lines) and a link to the release. **Update** installs it and restarts Tricot on the same address, with the same data folder and options; the page says "Updating to 0.2.0…" and reconnects by itself. **Skip this version** hides it until a newer one is out. How Tricot installs it depends on how you installed Tricot:

- With `npm install -g tricot`, when npm's global folder is yours: Tricot downloads the release's file into `update-download/` in the data folder, checks that its SHA-256 checksum is the one GitHub gives for it (for a release GitHub gives no checksum for, that its SHA-512 is npm's for that version; with neither, it won't install it and says why), checks that it is the Tricot package at that version, installs it with `npm install -g <that file>`, and deletes the download. That works where the npm registry is blocked. When the release came from npm instead, it runs `npm install -g tricot@<version>`. When npm's folder needs administrator rights (a Node installed for the whole system), Tricot shows the command to run yourself, with a Copy button: `npm install -g https://github.com/TricotStudio/tricot/releases/download/v<version>/tricot-<version>.tgz` (or `npm install -g tricot@latest` when the release came from npm), with `sudo` if that's how you installed it. Tricot never runs `sudo`.
- With Homebrew (`brew install tricotstudio/tap/tricot`): `brew upgrade tricotstudio/tap/tricot`, when Homebrew's folder is yours, or else that command to copy. The tap's formula installs the release's same file.
- With `npx tricot`: the new version, from npx's cache.

Anywhere else (on Windows, from a project's own `node_modules`, from a checkout) it shows the command to run instead. Every command runs as a program with its arguments, never through a shell. Before it restarts, Tricot checks that the new version is the one installed (`tricot --version`), so a Homebrew tap that hasn't caught up changes nothing. If the new version doesn't start, the old one is put back (from its own release's file, checked the same way, when GitHub has it) and started again; why is written to `update.log` in the data folder, and Tricot says so the next time you open it. A new version that changes how boards are stored keeps a copy of them in `backups/` first.

`tricot update` does the same from a terminal: it asks GitHub (or npm), then updates the board that is running, or installs the new version when none is. `tricot --version` prints the version you have.

To turn the check off, set `TRICOT_NO_UPDATE_CHECK=1`, or start Tricot with `--no-update-check`. It is off as well when Tricot runs from a checkout (`npm start`, `npm run dev`) and in tests. `tricot update` still asks when you run it.

## Configuration

| Variable | Default | |
| --- | --- | --- |
| `PORT` | `4545` | |
| `HOST` | `127.0.0.1` | Binding wider than this machine turns on the access token; see below. |
| `TRICOT_NO_UPDATE_CHECK` | | `1` turns off the daily check for a newer Tricot; see [Updates](#updates). |
| `TRICOT_DATA_DIR` | `~/.tricot` | `tricot.db`, one SQLite file holding every board and saved change by change, each board's event log and each block's earlier versions in tables of their own, read a page at a time (with its `-wal` and `-shm` files while a server runs; a copy is kept in `backups/` before any upgrade of its format), `assets/` for images, `server.lock` while a server runs, `seats.json` with the browsers and terminals you let act for you ([Seats](#seats)), and `token` once `HOST` is set beyond this machine. A data folder from one of the tool's earlier names is moved here on the first start. Boards from versions that kept one JSON file each are imported into the database on the first start, checked against it, and the files kept in `backup-json-<date>/`. The copies in `backups/` are whole databases, taken before upgrades, so a board you deleted can still be in an older one; delete old backups to be rid of it (deleting a board does remove its file from `backup-json-*/`). A database saved by a newer Tricot is refused, untouched. |

On `127.0.0.1` (the default) there is no token: one kept in your data folder couldn't stop a program running as you, and would only make every agent reconnect. What can still reach a local server is a web page open in your browser, so requests that carry an `Origin` other than the server's own are refused (403), and requests addressed to other hostnames are rejected (DNS-rebinding protection). No other site can show Tricot inside a frame of its own, either, and any request another site's page makes to Tricot (the browser says `Sec-Fetch-Site: cross-site`), such as a picture or a script pointing at the API, is refused (403), except opening Tricot in a tab and a connector's sign-in coming back. Agents and `curl` send neither header and pass. Tricot's pages carry a Content-Security-Policy that runs only Tricot's own scripts (and Google's Picker), frames only the players and viewers a link card opens in place, and shows pictures only from Tricot itself and `data:` URLs, so no picture on a board tells another site, or a device on your network, when you open it. The data folder is made private to your account (mode 700) and the files Tricot writes are 600, so other accounts on the computer can't read your boards. An open folder is tightened on start when it is `~/.tricot`, is new, or already holds Tricot's boards, lock or token; any other `TRICOT_DATA_DIR` keeps its mode, with a note on how to run `chmod 700` yourself.

No token also means that any program running as you on this computer can reach a local board. Agents act through their MCP tools, as themselves. What a person does over REST comes in two tiers:

- **Shaping the board** (comments, reactions, canvas edits, threads, pairing, making a board, dismissing what needs you) is taken from Tricot's own page, or from a Tricot terminal registered with the board (`tricot claude codex`, the board picker). A plain call from `curl` or a script is refused (403), with a message saying that agents act through their MCP tools. This tells Tricot's page from a plain program, and no more.
- **What is consequential** (answering an agent's request for permission and reading what agents wait for, approving a commit, deciding, retiring, deferring or reopening a decision, marking a task ready or moving it on, deleting a board or a card, Tricot skills, live steps, connectors and updating) is taken only from one of your **seats**: a browser or terminal you let in.

### Seats

A seat holds a key that never leaves it. Your browser makes it with WebCrypto, as non-extractable, and keeps it in its storage for Tricot's address; a Tricot terminal keeps one in memory while it runs. Tricot keeps each seat's public key in `seats.json` in the data folder, so seats outlive restarts and updates. A seat signs each consequential request: its method, its path, a hash of its body, the time and a counter. Tricot refuses a signature that doesn't match, one more than two minutes off its clock, and a counter already used.

Letting one in takes one keypress or one click:

- **A browser.** The first time it does something consequential, the page shows a four-digit code and "Press y in the terminal where Tricot runs, or run `tricot seats`". The terminal where `tricot` runs the board (in the foreground), the Tricot tab of `tricot claude codex`, and `tricot seats` (for a board in the background) each show "A browser wants to act for you (Chrome on macOS, code 4271). Allow? [y/N]", once they are let in themselves; every browser you let in shows the same with Allow and Deny. Check that the codes match, press y or click Allow, and the page does what you asked. It asks once per browser, ever.
- **The first browser.** While the data folder has never had a seat, any Tricot terminal can let the first browser in with y, and that terminal is let in with it until it closes. That happens once per data folder, and the activity of every board says so ("let the first browser act for them"). If that wasn't you, run `tricot seats reset` (below) and let your browser in again.
- **A terminal.** A Tricot terminal can see that agents wait, but not what they ask, until it is a seat. Press y in the Tricot tab (or run `tricot update` or `tricot seats`) and your browser asks "Let this terminal answer for you?" with its code. One click, and the terminal stays a seat until it closes.
- Each request to be let in lapses after three minutes. Every one let in, removed or denied is said in the activity, and an answer to an agent says where it came from ("denied this in Chrome", "in Tricot's terminal").

"Your browsers and terminals", in the menu under your name, lists each seat with who let it in and when, when it was last used, and Remove; `tricot seats` lists them in a terminal. The last browser can't be removed, as nothing could then let a browser in again. If its key is lost (its site data cleared), stop Tricot and run `tricot seats reset`: it asks first, then lets every browser and terminal go, so answering agents, approving commits and the like wait until the next browser is let in, as the first one was, by a keypress in the terminal where Tricot runs. Let your own browser in first, before anything else asks. It refuses while Tricot runs on that data folder.

What seats stop: a program on this computer passing for Tricot's page, or registering a terminal of its own, can no longer do anything consequential as you, nor read what your agents wait for. What they can't stop, as nothing inside Tricot can:

- **An agent driving your browser.** Clicks in a browser you let in are yours as far as Tricot can tell. The Tricot tab is the stronger place to answer.
- **Anything that rewrites `~/.tricot` without a sandbox.** A program running as you can edit the data folder, `seats.json` included, or stop Tricot and start its own. Agents' own sandboxes are the boundary there.
- **The first browser.** Until the data folder has a seat, any Tricot terminal can let one in, so a program that gets there before you can let in a key of its own. It happens once, and it is announced on every board and terminal.

In network mode (below), the token stands for you on other devices: a request from another device with the token can do what a seat does, though answering agents and live steps stay on the computer Tricot runs on. From this computer, the token never stands in for a seat, whichever address a program uses.

When `HOST` is set to listen on the network (`0.0.0.0`, a LAN address), Tricot makes a token once (kept in `<data folder>/token`) and requires it on everything: MCP, REST and the UI. Agents send `Authorization: Bearer <token>` (or `?token=` on the MCP URL for a client that can't set a header). Open `http://host:port/?token=<token>` once in the browser: it sets an HttpOnly, SameSite=Strict cookie and the board works normally after. `tricot` and `tricot connect` print the commands with the token in this mode. Agents may attach images by local file path only while the server is bound to localhost. Images are stored under `TRICOT_DATA_DIR/assets`, accepted only if their bytes are PNG, JPEG, GIF or WebP, and served with `nosniff`.

Network mode is plain HTTP with a token, so the token and your boards cross the network unencrypted. Use it only on a network you trust, or reach the server over an encrypted path instead: an SSH tunnel to a server left on `127.0.0.1` (`ssh -L 4545:127.0.0.1:4545 <host>`), or Tailscale. The `?token=` address also stays wherever it is pasted or run, such as an agent's MCP settings and your shell history, so those deserve the same care as the token itself.

A board left on `127.0.0.1` refuses requests that came through a tunnel or a proxy (ngrok, cloudflared, `tailscale serve`, a dev proxy), which would make requests from anywhere look local and need no token. It tells them by the headers those add (`Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `CF-Connecting-IP`, `Tailscale-User-Login`, `Tailscale-User-Name`) and answers 403, pointing to network mode and its token. An SSH tunnel adds none of them and still works; network mode takes requests with them, as long as they carry the token.

## Google sign-in

Connectors → Google signs in with PKCE and a redirect back to this server on `127.0.0.1` (any port, so `tricot --port` works). It asks only for your email and `drive.file`: Tricot sees the Google Docs you choose with Google's Picker ("Choose a Google Doc" when adding a link, "Choose Google Docs" on the Connectors page, or "Choose in Google" on a doc's card), and nothing else in your Drive. Sign-ins made before this, with the wider scopes, keep working until you connect again.

**Tricot Studio: fill in the client once.** The client ships with Tricot, in `src/server/connectors/google/builtIn.ts`, so people only click Connect. Google treats a Desktop client as public (its ID and "secret" can ship); what protects a sign-in is PKCE and the loopback redirect.

1. In Tricot Studio's Google Cloud project, enable the Google Docs API, the Google Drive API and the Google Picker API.
2. Set up the OAuth consent screen (Google Auth Platform) and add the `drive.file` scope. It is not a sensitive or restricted scope, so it needs no security review.
3. Create an OAuth client of type **Desktop app**. Put its Client ID in `clientId` and its Client secret in `clientSecret`.
4. Create an API key, restrict it to the Google Picker API and to the HTTP referrers `http://127.0.0.1:*/*` and `http://localhost:*/*`, and put it in `pickerApiKey`. (The Picker's app ID is the project number, which is the digits that start the client ID, so there is nothing to add for it.)

Until `clientId` and `clientSecret` are filled in (values starting with `FILL_IN` count as empty), Tricot has no client of its own and asks people for one, as before: they create a Desktop client in their own Google Cloud project and save its JSON in the data folder as `google-client.json` (or the `client_secret_….json` Google downloads); to use the Picker with it they also add `"picker_api_key": "…"` inside its `"installed"` object. **A client file in the data folder always takes over from the built-in one**, and the Connectors page says which one is in use. None of these values is logged or sent anywhere but Google; the one thing the server hands the browser is a short-lived access token for Google's own Picker.
