# The tricot command

Back to the [README](../README.md).

## Commands

`tricot canvas` starts Tricot Canvas, the board of pages and files, and opens it ([below](#tricot-canvas)), `tricot status` shows where it runs, `tricot stop` stops it, `tricot connect` finds the agents on this computer and connects them all in one step, with their hook where they take one and the Tricot skill where they have skills, after one question (`--print` only shows what it would do; [below](#connecting-an-agent)), `tricot connect <agent>` connects one, `tricot connect [mcp-json|url]` shows what to give any other client, `tricot skill` shows the Tricot skill in your agents, or adds it or takes it out ([below](#the-tricot-skill)), `tricot claude` (or `codex`, `opencode`, `pi`, `omp`, `copilot`) starts the board and the agent together (below), `tricot --background` keeps it running after the terminal closes, and `tricot update` updates it (see [Updates](configuration.md#updates)). `tricot listen` is an agent's, not yours: one you connected on your own runs it in the background when its wait says so, to sleep until something on the board needs it ([who's here](how-it-works.md#whos-here)), and `tricot --help` leaves it out. `tricot show` is mostly an agent's too: it puts a page on the board from any agent's terminal, starting Tricot if it isn't running ([below](#showing-something-from-an-agents-terminal)). It uses one server per data folder (a `server.lock` inside it), so a second `tricot` reuses the first. `tricot --help` lists the commands and the options that go with starting the board, and `tricot <command> --help` says what that command does and shows only the options it takes (`tricot connect --help` has `--print` and `--yes`, `tricot steps --help` has `--agent` and `--project`). A command Tricot doesn't know is answered with the closest one: `tricot stats` says `Did you mean "status"?` When another `tricot` on your `PATH` is another version, that message names it ([below](#updating-and-removing-it)).

### Stopping the board

`tricot stop` asks the running board to stop itself, over HTTP, and ends it with a signal only when that can't be done: the board then saves its boards and lets go of its data folder as it ends. Asking is a person's to do, so it needs one of your seats, like `tricot update` ([below](#letting-a-browser-act-for-you)). On macOS and Linux a terminal that isn't let in yet goes straight to the signal, which also stops the board gently. On Windows a signal ends a program at once, so `tricot stop` shows a code and waits a minute for you to allow this terminal in your browser; without that it ends Tricot at once, and the last moments of work may not be saved.

### Letting a browser act for you

What is consequential (answering an agent's request for permission, deleting a board and the like) is done only from a browser or terminal you let in, once each ([Browsers and terminals you let in](configuration.md#browsers-and-terminals-you-let-in)). When `tricot` runs the board in the foreground in a terminal, that terminal asks when a browser wants to act for you: "A browser wants to act for you (Chrome on macOS, code 4271). Allow?", with **Yes** and **No** beside it and No marked. Check that the browser shows the same code; **y** lets it in, **n** or Enter says no, and ←→ move the mark first, if you would rather choose. It asks only then, reads keys only while it asks, and Ctrl+C still stops Tricot. It answers the very first browser, and having let that one in, is let in with it until Tricot stops; after that it answers every browser that asks.

For a board running in the background (`tricot -d`) or started elsewhere, `tricot access` does the same: it lists your browsers and terminals and those waiting, with their codes, and asks Yes or No for each waiting one, the same way. It answers the first browser as that terminal does; later ones once it is let in itself, from a browser you've already let in, which it asks for with a code. `tricot access revoke`, with Tricot stopped on that data folder, asks "Remove every browser and terminal you've let in?" (Yes or No, No marked) and lets them all go: the next browser is then let in as the first one was.

## Tricot Canvas

`tricot canvas` starts Tricot Canvas, the board of pages, threads, files and agents. It starts the way `tricot` does and takes the options `tricot` takes (`--port`, `--data`, `--board`, `--no-open`, `--no-ask`, `--verbose`, `--no-update-check` and `-d`/`--background`), on the same data folder, so your boards are the ones `tricot` opens, and anything else already kept there stays as it is for the next `tricot`. It opens the page in the browser and says in a few lines how to start or connect an agent (it asks no question about which agents to start: that is `tricot`'s), and a second `tricot canvas` while it runs finds the first, prints its address and opens it, as a second `tricot` does. `tricot status` and `tricot stop` work on it, and `tricot status` names it ("Tricot Canvas 0.2.0 is running"). `tricot update` restarts it as Canvas on the new version, on the same address and with the same options, and restarts the other edition as itself.

A data folder runs one Tricot at a time, so `tricot canvas` and `tricot` refuse while the other edition of Tricot runs on the folder, in one sentence that names the one that runs and says to stop it with `tricot stop`:

```text
<the one that runs> is already running on <data folder> (http://127.0.0.1:4545), so <the one you started> can't start on it: stop it with `tricot stop` first.
```

The lock file `server.lock` in the data folder carries which one holds the folder (`"edition": "canvas"`; a lock without it is the other edition's, as every Tricot before Canvas was). The agent commands (`tricot claude` and the others, `tricot show`) start Tricot the way `tricot` does when none is running, and use the one that is, Canvas included.

## Starting an agent with the board

Plain `tricot`, in a terminal, asks this first: *Start Tricot with an agent?* (or *Start an agent with it?* when the board runs already, under its address), with a row for each agent Tricot can start whose program is on your `PATH`, ticked as you left them the last time (kept in the data folder), else the first. ↑↓ move, Space ticks or unticks one, and Enter starts the ticked ones with the board, as `tricot claude codex` would, below. Esc, or Enter with none ticked, starts the board alone in this terminal (or leaves the running one as it is), as `tricot` always did, with a few lines under its address: the agents you can start with it (`tricot claude · tricot codex`), `tricot connect` to connect your agents for good, and `tricot connect --print` for every command by hand and any other client. It asks nothing without a terminal, with `--background` or `--no-ask`, or when no agent it can start is here. Whether each agent has the board for good isn't checked: started from here it has it for its session.

`tricot claude`, `tricot codex`, `tricot opencode`, `tricot pi` and `tricot omp` start the board in the background (or find the one already running on the same data folder, as `tricot` does), ask which board to work on, open it in the browser (not with `--no-open`), and then start the agent in this terminal, with the strip and the Tricot tab ([below](#several-agents-in-one-terminal)). The agent gets the board for this session only and its own settings aren't touched. Its first message tells it to use that board and start listening. When the agent quits, the command returns its exit code, and a board it started stops with it. If another `tricot claude` (or `codex`, `opencode`, `pi`, `omp`) is using that board, it keeps running until the last of them quits, and a browser tab doesn't count. If the command is killed outright or its terminal crashes, the board notices that no agent command is there any more, and stops by itself within half a minute. A board you started with `tricot` or `tricot start` or `tricot --background` keeps running when the agent quits, as before. `tricot stop` stops any board. The first time, it also asks about [live steps](#live-steps), as `tricot` does.

Without `--board <id>`, Tricot lists the boards updated most recently, with how long ago each was. Move with the arrow keys, pick with Enter, and cancel with Esc or Ctrl+C, which starts nothing. "＋ New board…" makes one, named after the folder unless you change it. The board picked in a folder starts highlighted there next time, because Tricot remembers it in its data folder (`folder-boards.json`), never in the project. The server reads it too: a board's repository is the one its agents were started in. Without a terminal, as in a script, it stops and asks for `--board`.

`--name` sets the agent's name on the board, `--model` and `--effort` what it starts on ([below](#the-model-and-thinking-level-an-agent-starts-on)), and anything after `--` goes to the agent (`tricot claude -- --strict-mcp-config`). Each agent is connected through its own per-session option, from its own docs:

- **Claude Code:** `--mcp-config` with the server as JSON, and the token, when the board needs one, as its `Authorization` header. If you already have a server named `tricot` in Claude Code's settings, its docs don't say which of the two it uses, so the session uses one or the other. Add `-- --strict-mcp-config` to use this one alone, which also leaves out your other MCP servers for that session. `--allowedTools mcp__tricot__*` lets Tricot's own tools run without asking, and `--settings` gives the session Tricot's hooks: its permission prompts come to the board, and its [live steps](#live-steps) too if you said yes to them. Whichever of those hooks your own `~/.claude/settings.json` runs already is left out, so nothing runs twice. The output says where approvals go.
- **Codex:** `-c mcp_servers.tricot.url=…` overrides, which rank above every config file. With a token, `bearer_token_env_var` names `TRICOT_TOKEN`, which is set in Codex's environment only. `default_tools_approval_mode="approve"` lets Tricot's own tools run without asking; your own `tricot` entry's other settings still apply. Codex takes hooks only from its settings, so its permission prompts come to the board once its live steps are on (`tricot steps on --agent codex`), and the output says which.
- **OpenCode:** the entry in `OPENCODE_CONFIG_CONTENT`, in its environment only, which OpenCode merges over its global and project config, and `--prompt` for the first message.
- **Pi:** `-e` loads a small extension for this run, which adds the board as an MCP server for the session (`pi.registerMcpServer`). The extension is a file in a private folder made for the session (in the system's temporary folder, with the board's address and nothing else in it) and removed when Pi ends; if Tricot is killed outright it stays, and the next `tricot` agent command removes such folders once they are a day old. Your `~/.pi` folder isn't touched, and Pi's sign-in, models and sessions are where they were. With a token, the entry reads it from `TRICOT_TOKEN`, set in Pi's environment only. A server named `tricot` in your own `~/.pi/agent/mcp.json` (from `tricot connect pi`) takes precedence over the session's, as Pi's docs say. Pi reaches the board's tools through its `codemode` tool, as when you connect it by hand.
- **OMP:** `-e` loads an extension folder for this run, and OMP reads the MCP servers a `.mcp.json` in it holds. The folder is private, made for the session, holds that one file and is removed when OMP ends (one left by a Tricot killed outright is swept like Pi's); your `~/.omp` folder isn't touched, and OMP's sign-in, models and sessions are where they were. With a token, the entry reads it from `TRICOT_TOKEN`, set in OMP's environment only. The session's entry ranks below one named `tricot` in your own `~/.omp/agent/mcp.json` (from `tricot connect omp`) and above the Claude Code, Codex and Gemini CLI files OMP also reads, so OMP gets its own entry, with the timeout its waits for the board need. (With Claude Code's entry it would still show on the board as "OMP", which Tricot reads from its MCP client, but its calls would give up after 30 seconds.)
- **Copilot CLI:** `--additional-mcp-config` with the server as JSON, which takes the place of a server named `tricot` in your own `~/.copilot/mcp-config.json` for this session, and `--enable-mcp-server=tricot` in case you turned yours off. With a token, the entry's header names `TRICOT_TOKEN`, which Copilot fills in from its environment, set there only. `--allow-tool=tricot` lets Tricot's own tools run without asking, and `-i` is the first message.

If the agent isn't on your `PATH`, Tricot says how to install it and starts nothing, not even the board. Gemini CLI has no per-session option that leaves its settings alone (it adds a server only from a settings file), so `tricot gemini` starts nothing, neither the agent nor the board. The same goes for `tricot goose` and `tricot hermes`: Goose's flag for one session names the server after the address and can't send the board's token, and Hermes Agent adds a server only to its config file. Grok Build is the same: its interactive mode reads MCP servers only from its config files and installed plugins.

What these commands do instead depends on the board. With one running on this data, `tricot gemini` says which (its address, and so its port, and its data folder: `tricot` and a development copy on another port and folder each look at their own), then connects Gemini CLI as `tricot connect gemini` does: it shows the command, asks, and runs it on yes. An agent that can say what it has under the name `tricot` is asked first, and one that has this board already isn't asked anything; Gemini CLI and Grok Build can't say, so Tricot says so and asks, No marked (Gemini CLI replaces its `tricot` server when added again). Goose and Hermes Agent get Tricot's entry in their settings file, after asking, as `tricot connect goose` adds it ([below](#connecting-an-agent)). It then asks which board with the same picker as `tricot claude` (or takes `--board`), and prints the sentence to give the agent once you start it yourself: `Use the Tricot board <id> and start listening.`, the first message `tricot claude` gives its agent. With no board running, it prints how to connect the agent (as `tricot connect gemini --print` does) and the data folder and port it looked at. Without a terminal it asks nothing: it prints how to connect the agent, and the sentence when `--board` names a board.

### The model and thinking level an agent starts on

Each agent starts on the model and thinking level set for it in its panel (open it from the menu under your name): a chip beside its name says it ("Opus · high"), or "Its own settings" when nothing is set, and opens a list of both, with a field for a model of your own. It is the same on every board, kept in the data folder (`agent-rules.json`) rather than in a board, and only you change it, from a browser you let in; agents can't. Default passes nothing, so the agent's own settings apply, as before. A change takes effect the next time Tricot starts the agent, and the line under its name says what it runs on now: "Running on Opus · high", or "On Opus · high till it restarts". An agent you started yourself says nothing there.

`--model` and `--effort` after an agent's name stand in for its rule for that run, one by one: `tricot claude --model opus --effort high codex --model gpt-6.1-sol`. With one agent they can come anywhere; with several, one before every agent's name is refused. `--effort` is Tricot's one name for the thinking level, given to each agent in its own words, and refused for one that has none Tricot can set. A value that starts with `-` or holds a control character is refused, and each value is its own argument, never through a shell.

| Agent | Model | Thinking level |
| --- | --- | --- |
| Claude Code | `--model` (`opus`, `sonnet`, `haiku`, `fable`, or a full name) | `--effort`: low, medium, high, xhigh, max |
| Codex | `--model` | `-c model_reasoning_effort="…"`: low, medium, high, xhigh, max, ultra |
| Pi | `--model` (a pattern it matches) | `--thinking`: off, minimal, low, medium, high, xhigh, max |
| OMP | `--model=` (a pattern it matches) | `--thinking=`: off, minimal, low, medium, high, xhigh, max, auto |
| OpenCode | `--model` (`provider/model`) | none |
| Copilot CLI | `--model` (a model's id, or `auto`) | `--reasoning-effort`: low, medium, high, xhigh, max |

The strip at the bottom of the terminal says what each was started on after its name (`○ 1 Claude · Opus high · Running npm test`) while the line has room for it and the keys.

For one message, tag the agent instead: `@Claude:opus:high` asks Claude to do that message's work on Opus at high thinking, and its session and its rule stay as they are. Either part can be left out (`@Claude:opus`, `@Claude::high`). It is still a mention of Claude in every way (who hears it, delivery, the chips, notifications); the agent's updates add "asks you to do this on opus at high thinking: hand the work to a subagent on that model and thinking level, and keep your own session as it is". Only Claude Code can do this for now, through a subagent (its Agent tool takes `opus`, `sonnet`, `haiku` or `fable`, so a full name goes by its family: `claude-opus-4-5` is `opus`). The other agents use their own model and thinking for the message, and Tricot says so before you send it; the message still goes. A thinking level must be one of the agent's own, and a model is refused as on the command line; a model whose name holds a colon can't be tagged. A tag goes only on an agent's mention: `@Sam:later` and `sam@example.com` read as they always have.

### A coordinator, and the agents it starts

Every agent this command starts, and Tricot wakes, is a coordinator of the board (`src/core/roles.ts`): `tricot claude` starts one, `tricot claude codex` two, and one added from the Tricot tab is one too. A coordinator answers what people ask in the chat bar and hands each piece of work to a thread an agent owns; with several, a message that @-mentions one goes to it, and one that mentions none to the one active last. For new work it starts that thread, and this terminal starts its owner in a tab of its own, of the coordinator's own kind unless it says otherwise, named after the thread (*Claude · Sign-in flow*, *Codex · Dark logo*), on the board and with the thread to own; the owner runs its own subagents as scouts and workers, and says in the thread where the work stands. Each coordinator runs at most three owners at work at once, or as many as its agent's panel says (the rule chip's Coordinator row, *At once*, from 1 to 8, read again within half a minute of a change); a thread waits for a free one, and an owner that ended is started again after two minutes while its thread is still at work. An owner whose thread waits on you, or is done, doesn't count: it sleeps, at no cost, so a word in its thread finds it with all it knew. It closes when you delete its thread, a minute later so Undo still finds it there; when its thread is done and it has slept for an hour, once its tab isn't the one showing; or when the terminal needs its tab for new work (it holds nine): then the done one quiet longest closes. A word in a done thread later starts a fresh owner, which reads the thread back. With coordinators in several terminals, each starts only the owners of its own kind. An agent Tricot can't wake answers as any agent does, and the start says so. Each role starts on the model and thinking level set for it: the rule chip in the agent's panel has a row for the agent itself, its Coordinator, its Orchestrators, and the Scouts and Workers an orchestrator runs. A coordinator's or an orchestrator's left at *As Claude* takes the agent's own; scouts and workers left at *Its choice* are the orchestrator's to pick, and one set is told to it as it starts.

### Several agents in one terminal

`tricot claude codex` (any of `claude`, `codex`, `opencode`, `pi` and `omp`, in any order) starts the board and asks which board once, then starts each agent exactly as above, with its own name on the board, all in this terminal. One tab shows at a time, and a strip on the bottom line lists them all, each agent with what it is doing: its latest step on the board, "waiting for your OK" when its request for permission waits on the board, "wants you" when a hidden one rings its bell, "listening on the board", or, without live steps, whether it is drawing. One that quits says "ended", with its exit code when that isn't 0, and keeps its place. One you stop from the Tricot tab leaves the strip at once, and those after it move up a number.

The first tab is Tricot's own, and it opens on the chat: the board's conversation, as its *Home* shows it on the page, oldest at the top and scrolled to the latest. It holds what you asked, from the page's chat bar or from here, and what the coordinator answered, each with who said it and when, and the day between them. Under an ask the coordinator sent on, a card names the thread it went to, its agent and where its work stands (Starting, At work, Needs you, In review, Done); an ask whose own thread an agent took on says who took it. What of that work needs you comes into the conversation at when it was said: an agent's question to you, in full, which folds to who answered and what they said once someone has, work waiting for your review, with its summary in full and a line saying to approve it or send it back on the board (a reply here is a plain one, which leaves it waiting), which folds to your verdict once you gave it, and a thread done, with the first line of its summary. What came while you were away (the chat out of sight, in an agent's tab or the status view, for two minutes or more) is under *Since you were last here*, and the relays among it come as one, what needs you first. At its left runs the yarn, as beside Home: the conversation's strand, with a stitch (•) at each message, and a lane for each thread an agent owns, in the colour of where its work stands, which knits off (├─╮) at the card that sent it on, stitches into each of its relays and is tied off with a knot (●) where its work was done. A window too narrow for the lanes keeps one column of marks beside the conversation's strand instead, and a terminal that draws no colour (`NO_COLOR`) draws the yarn in plain characters, each lane's own character saying where its work stands (`|` at work or done, `!` waiting on you or your review, `:` not started). The rest of a thread's messages, the comments on a pinned part of a canvas, progress notes, activity and requests for approval are not in it: a thread is read on its own (below), comments on the page, and the rest in **/status**. New messages and relays arrive live, as on the page; **↑ ↓**, Page Up, Page Down, Home and End scroll while nothing is typed, and a stream scrolled up stays where it is, the row above the line saying how many newer messages are below. **Enter** takes it back to the latest: on an empty line that is all it does, and with something typed it sends it and goes there.

Under the stream, what you type answers the latest message from someone else, in its thread, or the latest question relayed that waits on you, in the thread it was asked in, sent as you and shown at once. The row under the line says where it goes and who hears it, for example "to Sign-in on mobile, the latest · Claude · Sign-in on mobile hears it". A message that arrives while you type doesn't move it; once the line is empty again, it follows the latest. When nothing in the stream is from someone else, the line starts a thread, and says whom it asks as Home's bar does: the board's coordinator, else its one agent ("Ask Claude, or give it work…"). A question relayed while its thread waited on you stays, answered, once the thread moves on, for as long as this terminal runs (the page remembers it in its browser); one asked and answered before the terminal started is not relayed here.

To send elsewhere, begin with **@** and a name to start a new thread aimed at that agent (it is then picked, as from the threads' panel below, and **Esc** brings you back to the whole stream), or with **>** and part of a thread's title. **Tab** completes the name or the place, listing each place with its title; a place the board doesn't have says why and sends nothing. A **>** followed by a space is plain text. With nothing typed, **Tab** chooses what to answer or open, marked ❯: the latest of what others said, the cards under the asks and the relays, then each **Tab** (or **↑**) one further back and **Shift+Tab** (or **↓**) one later. What you type then answers it where it is (a card, in the thread it leads to), **Enter** on the empty line opens a card's or a relay's thread as picking it from the threads' panel does, and **1 2 3** leave 👍 👎 👀 on a message or take yours back. A thread whose latest message you have read in the stream no longer waits on you in **/threads**. Letters such as **y**, **n**, **x** and **q** are text while you chat: they answer requests or stop agents only in the status view (from the chat, type **/stop** or **/quit**).

After an agent's name, **:** starts a tag for that one message ([above](#the-model-and-thinking-level-an-agent-starts-on)): the row above the line lists the agent's models and **Tab** writes each in turn, as it does a name (a colon typed just after a name **Tab** wrote takes the place of its space), and after a second **:** its thinking levels. Any other model can be typed. The row under the line adds what the message runs on ("to Claude, on Opus at high thinking · Claude is listening: this is seen at once."), or, in the alert colour, that the agent can't switch models for one message and will use its own, or what is wrong with the tag.

Type **/** to see local commands alongside agent skills. Local commands say “Tricot command”; an agent skill names its agent and completes to **@Agent /skill**. Use **Tab** or the arrow keys to choose, then **Enter**; the row under the line says what the command does. A command on its own runs here and is never sent to the board; a message such as **@Claude /status** still goes to that agent.

- **/status** opens the agents, approval requests and board activity.
- **/threads** opens the threads in a panel beside the stream, with what waits on you first.
- **/new** goes back to the stream, with the line starting a new thread; **Esc** goes back to answering the latest.
- **/add** lists the agents that aren't running, as **a** does in the status view, at the foot of the chat: pick one with the arrow keys and **Enter**, or by its number. One that Tricot can't start says why. **Esc** goes back to the chat.
- **/stop** lists the agents that are running, as **x** does, then asks "Stop it?" with **No** selected. **Esc**, or No, goes back to the chat.
- **/open** opens the board in your browser, as **o** does.
- **/quit** quits and closes every agent, as **q** does.

What **/add**, **/stop** and **/open** did shows under the chat for a few seconds, or until your next key. Answering a request (**y**, **s**, **n**) has no command: it acts on the request picked in the status view.

In the status view or the threads' panel, **/** opens a line of these commands without changing an unsent message. **Esc** cancels that line; in status, **Esc** returns to chat. A command picked on the status view's line acts there, its list at the foot of the status view. In the stream, **Esc** clears what you typed; with nothing typed it goes back from a message chosen to the latest, then from a thread picked to the whole stream, and then opens the threads' panel. Requests for approval stay visible while you chat, with **/status** beside them.

The TRICOT wordmark stays at the top, with the board's title and address beside it. It knits up once in under a second; any key finishes the animation and still acts as typed. `TRICOT_NO_ANIMATION=1` shows it whole at once, and a small window uses a one-line header. Switching tabs does not replay the animation.

The threads' panel lists the board's conversation as one row, **Conversation**, where your quick questions and their answers are (• when something in it is new to you; **Enter** on it closes the panel on the whole stream, which holds them), then the work handed out: what waits on you first (● waiting on you, • replies you haven't seen), then the rest by when they were last active, and the quiet finished ones under Earlier, with **Show N more**. From about 100 columns it sits at the stream's right, about a third of the width, the stream still in view beside it; in a narrower window it covers the stream. While it is open, **↑ ↓** move through its threads and **Enter** picks one: the stream then shows only that thread's messages, scrolled to its latest, under a row that says so ("Only Picker spacing · Esc for everything"), and the line answers it, the row under it saying who hears it ("to Picker spacing · Claude hears it"). An **@** at the start of the line is then a mention in the thread, not a new one. **Enter** sends your reply as you; a refused send keeps your text and says why. With nothing typed, **Tab** chooses one of the thread's messages from someone else, **1 2 3** leave 👍 👎 👀 on it or take yours back, and **Ctrl+L** sets the thread's lens. **Esc** goes back a step at a time: from the thread picked to the whole stream, the panel still open with that thread highlighted, and then closes the panel (back to the status view when **t** opened it there). In a narrow window a thread picked takes the whole window, and **Esc** brings the panel back before closing it. In the panel, **n** starts a new thread as **/new** does, and **l** (or **Ctrl+L**) sets the highlighted thread's lens, the lenses listed in the panel's place. The panel stays as you left it while you look at an agent's tab or at **/status**.

In **/status**, **y** allows the selected request, **s** allows it for the session where offered, and **n** denies it after an optional reason. **← →** choose an answer, **Enter** confirms it, and **↑ ↓** choose another request. The default is Deny, so a stray Enter never allows one. **o** opens the board in your browser, **t** opens the chat with the threads' panel, **a** adds an agent, **x** asks which agent to stop and confirms with No selected (the agent leaves the strip and the list at once, which makes room to add another: one terminal holds nine), and **q** quits. A request answered here and on the page can cross: the first answer wins. When a request arrives while an agent's tab shows, the strip tells you. Once every agent has ended, Tricot's tab stays until you quit or add one.

In the threads' panel, **x** asks to delete the highlighted thread, in the panel's place, with **No** selected. Choose with **← →** and confirm with **Enter**, or answer with **y** or **n**; **Esc** and **Ctrl+C** cancel. **u** undoes your latest deletion in this terminal, including when the panel is empty.

**Ctrl+\\** shows the next tab, and the one after it each time you press it again, round the strip from the last tab to the first. Ctrl+\\ is Tricot's alone: it never reaches an agent. Within a second after a press, **0** shows the Tricot tab and a number shows that agent, **q** quits (every agent is closed, as closing the window would), **[** scrolls back through the history of an agent that has one (of the tab you were on before the first press). The arrow keys go to the agent as usual. Ctrl+Z does nothing here, as an agent stopped in a hidden terminal couldn't be brought back.

A click on the strip shows the tab you click, from any tab. For this, Tricot keeps your terminal reporting the mouse all the time, so a plain drag no longer selects text: hold **Shift** while you drag (**Option** in iTerm2). An agent that turned the mouse on itself still gets what it asked for above the strip: its clicks, drags and wheel. Otherwise clicks above the strip do nothing, and the wheel scrolls: the chat in the Tricot tab, an agent's history as **[** does (scrolling back down to the bottom returns to the agent), or, for an agent that draws its own screen, ↑ and ↓ as your terminal would send them.

Each agent runs in a pseudo-terminal of its own, made with the Perl that ships with macOS (then Python's `pty`, then the `script` command), so nothing is installed. Hidden agents keep running and get their startup questions answered; your terminal's input settings follow the agent showing (but for the mouse, above), and a resize reaches all of them. Claude Code runs in its full-screen renderer here. When you quit, the terminal is put back, the board stops if this command started it and no other agent command needs it (as above), and the command returns the first exit code other than 0, in the order the agents were named and then added (an agent still running when you quit, or stopped from the Tricot tab, was closed, not failed).

To answer from its tab, the terminal is let in once, as a browser is (see [Browsers and terminals you let in](configuration.md#browsers-and-terminals-you-let-in)). Until then the tab shows that an agent is waiting, but not what it asks, and **y** asks to let the terminal answer: your browser shows "Let this terminal answer for you?" with the code the tab shows, and one click there lets it in until it closes. The tab registers with the running board as it starts, and makes the key it signs with; it keeps both in memory only (never in a file, an environment variable or an argument, so the agents it starts never see them) and lets go of them as it ends. When a browser asks to act for you, the tab asks too: "A browser wants to act for you (Chrome on macOS, code 4271). Allow? [y/N]". **y** allows it, **n** or Enter denies it, Esc leaves it for the board; while no browser has ever been let in, any Tricot terminal answers it, once, and is let in with it.

It needs a terminal, and doesn't work on Windows yet.

One agent runs this way too: `tricot claude` shows Claude Code with the strip at the bottom and the Tricot tab beside it, so the process view is there with one agent as with several. `--name` and words after `--` name one agent, so they work with one (`tricot claude --name Reviewer -- --strict-mcp-config`), and are refused with several; `--model` and `--effort` go after each agent's name instead. Where the strip can't run (Windows, no terminal, or no way to give the agent a terminal of its own), one agent runs on its own in this terminal, as [above](#starting-an-agent-with-the-board), and says why when your terminal could have had it; several agents are refused there. Gemini CLI can't be started this way either, as above.

## Showing something from an agent's terminal

When you ask an agent in its own terminal to show you something on or in Tricot, the board or the canvas ("show me the sign-in flow on Tricot", "show me the last dev log in tricot"), and its Tricot tools aren't there because Tricot wasn't running when it started or it was never connected, the agent runs `tricot show`:

```sh
tricot show flow.mmd timing.csv --title "Sign-in flow" --agent claude --asked "show me the sign-in flow"
```

- **Tricot:** the board running on this data folder, or one started now in the background, as `tricot --background` starts it; the command waits until it answers. It keeps running after the command ends, so you can open the page, until `tricot stop`.
- **The board:** `--board <id>`, else the board used in this folder or the nearest folder above it (not your home folder's), as `tricot claude` remembers it in `folder-boards.json`. When neither says, or the board named isn't there, it lists the boards with their ids and exits 2, adding nothing: the agent asks you which, then runs it again with `--board <id>`, or with `--new-board <name>` when you want a new one. It never makes a board you didn't ask for. The board it used is remembered for the folder, so the next page goes there without asking.
- **The page:** a Sketchbook page titled `--title`, made as the agent `--agent` names (an id such as `claude` gives its name on the board, Claude; any other name is taken as it is), never as you: the command connects to the board's MCP endpoint under that name, as the agent would, and makes it with the agent's own tools. The page keeps the agent and `--asked`, what you asked in your words, and says so under *Pages* (*Asked in Claude Code: “show me the sign-in flow”*); what you ask on the page then goes to that agent.
- **The blocks:** one for each file named, in that order, by its extension: `.md` and `.txt` a note, `.mmd` and `.mermaid` a Mermaid diagram, `.csv` and `.tsv` a table (its first row the columns), `.png`, `.jpg`, `.gif` and `.webp` an image, and any other file code, named by its path in the folder. `-` reads one block from stdin, a note unless `--as diagram`, `table` or `code` says otherwise, and `--text "<words>"` adds a short note first. Files rather than a flag for each kind: a file is what an agent has already or writes in one step, its extension says the kind, and several blocks are several names.
- **The link:** the board's address and the page's, as `add_page` gives it, printed on its own line for the agent to hand you, with the commands to add to the page and to listen on it.

`tricot show --page <id> <files>` adds blocks to a page already there. What you then ask the agent on the page, in the chat bar over it or about blocks you select there, reaches it this way too:

- `tricot show --listen --page <id> --agent claude`, which the agent runs in the background, waits until you ask it something on that page, prints what you said, who said it and how to answer, and ends, which wakes an agent that runs it so (Claude Code starts a turn as a background command ends). It counts from the agent's last doing on the board, so what you wrote while it was between commands isn't missed, and never wakes for the agent's own messages or for anything elsewhere on the board. Meanwhile the board shows the agent asleep, to be woken, as it shows one Tricot's terminal holds; it reads the board as a page does, so nothing counts as read by the agent until it prints it.
- `tricot show --page <id> --reply "<words>" [files] --agent claude` answers it, as the agent: in the page's thread, with the files as blocks on the page shown under the reply (for a thread about blocks you selected, they go in the group beside them; the agent talks it through in words first, and adds files only once you ask for something made); or, for an ask about blocks you selected made before a message sent with blocks selected began a thread, with the words and the files as blocks in the group beside them, which finishes the ask. `--to <id>`, as `--listen` printed it, says which; without it, the latest.

Everything it can check without the board (no `--agent`, no title, a file it can't read) is refused before it starts anything.

## Connecting an agent

`tricot connect` connects every agent on this computer in one step. It looks for each agent Tricot knows: one that joins through a command of its own (Claude Code, Codex, Pi, Gemini CLI, Grok Build, Copilot CLI) by its program on your `PATH`; one that joins through its settings file (OMP, OpenCode, Goose, Hermes Agent) by its program, or by that file. It reads whether each already has this board, as below, and shows one list with a line for each agent: those already connected marked ✓, those it can't connect marked – with why, and the rest ticked, with a note only where there is something to decide (a server named `tricot` at another address, or why one can't be connected). The list opens with an All agents row that ticks every row, those at another address too, and clears them all again (`a` does the same from any row); it shows [-] while only some are ticked. One sentence under the list says what else a tick adds (live steps, a skill). ↑↓ move, Space ticks or unticks one, `?` shows everything it would change (each file the hook and the skill add, the copies it keeps, what is sent, how to turn it off, and each command it runs) and then the list again, and Enter connects the ticked ones, one after the other; Esc changes nothing. It ends in a few short lines: what is connected (start a new session of each), what it left alone, and how to turn the live steps off, then what wasn't connected and why, with how to connect each of those yourself (for a file it couldn't edit, the entry to paste). An agent with a server named `tricot` at another address (another board, or a port that moved) starts unticked: ticking it replaces that server, which `--yes` never does. `--yes` connects the ticked ones without asking; `--print` shows the whole text (each row in full, with the command or file it would use, and the hook's and the skill's explanations) and each entry it would add, and changes nothing. Without a terminal to ask in it changes nothing either, and says to add `--yes`, in the short form. Where there is a terminal but no keys to tick with, it asks once, Yes or No, for the ticked ones, and says which of them also get the hook and the skill. `--name` goes with one agent only, as one name for every agent would name them all the same. The exit code is 1 when an agent found here was left unconnected for a reason other than you unticking it.

The same question covers the hook, for every agent that has one. The hook is what `tricot steps on` sets up for the agent ([Live steps](#live-steps)), and Tricot reads which agents have one, and which of those take a prompt hook, from their live-steps installers, never from a list of its own. Every agent with an installer gets its live steps: its steps on the board and, for Claude Code and Codex, its permission prompts on the board. An agent whose installer has a prompt hook (the agents the lens paragraphs of Live steps list) gets that with it. The other agents with live steps get live steps only, and an agent with no installer (Cursor) gets no hook. `?` in the list, and `--print`, say what each kind does and sends, in the words the first `tricot` uses: the prompt hook adds a short line for the agent when you ask to see something on Tricot, or open a message with a lens (`^Design`), and sends none of your words anywhere; an agent with live steps only is told Tricot has no prompt hook for it, so a request to see something on Tricot, or a lens, reaches it as you typed it, and it goes by the wording of Tricot's tools to make a page; each hook sends one line per step, the agent's to-do list as it writes it and the names of the files it changes, never file contents, command output or your prompts. They list the files it adds for each agent (`tricot connect --print` shows every line), and the sentence under the list says which agents also get live steps. A yes connects each ticked agent, then sets its hook up; nothing is written without it. Before it changes a settings file, it keeps a copy beside it as it was (`settings.json.tricot-backup`, as for an agent's file below), taken before anything is written, so a file the agent's own command changes too (Gemini CLI's `settings.json`) is kept as it was; the files the hook only creates (its scripts, a plugin or an extension folder) have nothing to copy. An agent already connected with no hook yet is ticked for the hook alone. The answer, yes or no, is kept per agent in the data folder (`live-steps.json`), the file the first `tricot`'s question uses: an agent answered here is not asked about at the first `tricot`, one answered there is not offered the hook here, and unticking a row, or answering no, counts as a no. Esc keeps no answer. The first `tricot` still asks about an agent nobody has answered for, one installed after `tricot connect` ran. An agent whose hook is on already, or that you answered for earlier, is left as it is, and the result says so, with `tricot steps on --agent <id>` to add it later. A settings file the hook can't read is left as it is, and the agent is still connected. An agent whose connection couldn't be made, or that you left unticked, gets no hook. `--yes` covers both halves for the ticked rows (it never replaces a server at another address, hook or not), and `--print` shows each hook's exact files and lines too. The ending says which agents it connected, and adds a line for a hook that already was, one you answered for earlier, or one that couldn't be added, with `tricot steps on` to add it later; `--print` says which agents have live steps only and which have no prompt hook. The exit code is also 1 when a hook couldn't be added.

The same question covers the Tricot skill, for every agent that has skills ([The Tricot skill](#the-tricot-skill)): Claude Code and Codex today. Which agents have one is read from the registry (a `skill` in an agent's server half), never from a list in `tricot connect`. `?` in the list, and `--print`, say what the skill is and the one file it adds for each agent, and the sentence under the list says which agents also get it. A yes writes each ticked agent's skill file; nothing is written without it. No settings file of the agent is read or changed: the skill is one plain file in the agent's own folder. It goes in even where the agent's connection didn't go through, since it is for when the agent's tools are missing. The answer, yes or no, is kept per agent in the data folder (`skills.json`), apart from the hook's: an agent that answered the hook's question before the skill existed is still offered the skill, a no is not asked again, and the first `tricot` asks only about live steps, so it never asks about a skill. An agent already connected with no skill yet is ticked for the skill alone. `--yes` covers it for the ticked rows, and `--print` shows each skill's exact file. The ending says which agents got the skill, and adds a line for one that already had it, one left as it was and why; `--print` says which agents have no skill to add yet. The exit code is also 1 when a skill couldn't be written (a link or a folder in its place).

An agent that joins through its settings file gets only Tricot's entry, named `tricot`, under the section that holds its servers (`mcpServers` in `~/.omp/agent/mcp.json`, `mcp` in `~/.config/opencode/opencode.json`, `extensions` in `~/.config/goose/config.yaml`, `mcp_servers` in `~/.hermes/config.yaml`, each in the folder the agent's own variables move it to: `XDG_CONFIG_HOME`, `HERMES_HOME`, `%APPDATA%` for Goose on Windows). Before it writes, Tricot keeps a copy of the file as it was beside it (`opencode.json.tricot-backup`, readable by you alone, in place of any copy an earlier connect kept), and it writes the file whole or not at all, with the mode it had. Every other line stays as it was: the file is never read and written back whole, which would lose comments and spacing. In JSON (comments and trailing commas allowed, as OpenCode reads them) the entry is spliced in after the section's last server, indented as its neighbours, and the result is read again and must be the file's own value with that one entry added, or nothing is written. YAML has no reader in Tricot, so it edits only the layout people and the agents write: a mapping at the top, the section a block of one entry per name (or empty), the entry added after the last one or put in place of Tricot's own. A file it can't read as its format, or laid out otherwise (tabs, more than one document, the section on one line or as a list), a link (a dotfiles folder's: Tricot doesn't write through links), or one Goose or Hermes Agent writes itself the first time it runs and hasn't yet, is left as it is, with why, and the entry to paste. A JSON file that isn't there yet is made with the entry alone. The entry never holds the board's token: it names `TRICOT_TOKEN`, which the agent reads from its environment.

`tricot connect claude` connects Claude Code, and `codex`, `pi`, `gemini`, `grok` and `copilot` connect theirs: Tricot shows the agent's own command, says which of its settings it changes (a server named `tricot`, in `~/.claude.json`, `~/.codex/config.toml`, `~/.pi/agent/mcp.json`, `~/.gemini/settings.json`, `~/.grok/config.toml` or `~/.copilot/mcp-config.json`, for every session), asks whether to run it (Yes or No, No marked), runs it, and says whether it worked. Before it asks, it reads what the agent already has under the name `tricot` (`claude mcp get tricot`, `codex mcp get tricot`, `copilot mcp get tricot`; Pi, Gemini CLI and Grok Build have no such command, so for them Tricot only adds). When that is already this board's address, it says "Claude Code is already connected to this board. Nothing to do." and runs nothing. When it is another address (another port, or another `--name`), it says what it found and asks once whether to replace it, running the agent's `remove` and then its `add`; it never replaces with `--yes` or without a terminal, and says the commands to run yourself. If the agent refuses, its own message is shown and the exit code is 1. `--yes` skips the question and still shows the command.

`--print` shows the command and runs nothing: for scripts, and for an agent that isn't installed on this computer. Tricot runs nothing either, and prints the command the same way, when there is no terminal to ask in and no `--yes`, or when the agent isn't on your `PATH`, and says what to do. It runs the command without a shell, with 30 seconds to finish.

`tricot connect omp` (and `opencode`, `goose`, `hermes`, `cursor`) connects that agent through its settings file, as above: it says what it would add and where, and that it keeps a copy, asks (Yes or No, No marked; `--yes` skips the question), and adds it. As with a command, an entry for this board already there means nothing to do, and one for another address is replaced only on a yes to the question that says so. `--print` shows the entry and changes nothing, as it always did. `mcp-json` and `url` are an entry and an address for any other client, so `tricot connect` only shows those. `tricot` itself, when it starts the board alone, says in a few lines how to start an agent with it or connect one; each agent's command by hand is `tricot connect --print`'s.

The same by hand, for Claude Code (or any MCP client that speaks Streamable HTTP, by its address):

```sh
claude mcp add --scope user --transport http tricot http://127.0.0.1:4545/mcp
```

Without `--scope user`, Claude Code keeps the server for the one folder you ran the command in.

Add `?agent=Name` to the URL to label an agent on the board, e.g. when several agents share one board. Without it, the MCP client's own name is used. A URL that names another agent Tricot knows (OMP using Claude Code's `?agent=Claude`, say) is taken as borrowed: the agent shows by its own usual name, read from its MCP client.

Cursor editor and CLI share MCP settings. `tricot connect cursor` adds Tricot
to `~/.cursor/mcp.json`, preserving other servers and keeping a backup.
`tricot connect cursor --print` shows the entry without changing anything.
For one project, merge that entry under `mcpServers` in `.cursor/mcp.json`.
Plain `tricot connect` detects Cursor from `cursor` on PATH or an existing
`~/.cursor` settings folder, even before its first MCP file exists.
Enable or approve Tricot in Cursor if prompted; in the CLI run
`agent mcp enable tricot`. On a token-protected board, set `TRICOT_TOKEN` in
the environment Cursor runs from; the header uses `${env:TRICOT_TOKEN}`.
Tricot does not start Cursor sessions or provide Cursor live steps, approval
forwarding or usage reporting yet. See [Cursor MCP configuration](https://cursor.com/docs/mcp)
and [Cursor CLI MCP](https://cursor.com/docs/cli/mcp).

## The Tricot skill

When you ask an agent to show you something on or in Tricot, the board or the canvas ("show me the last dev log in tricot", "put the auth flow on the board", "draw the architecture on the canvas"), it should put it on a Sketchbook page and hand you the link, even with Tricot stopped and its Tricot tools missing. The Tricot skill is how, for every agent that has skills. `tricot connect` adds it with the connection (above); `tricot skill` looks at it, adds it later or takes it out.

It is one file, `tricot-show/SKILL.md`, in the folder the agent keeps its personal skills in: `~/.claude/skills` for Claude Code (`CLAUDE_CONFIG_DIR` moves it) and `~/.codex/skills` for Codex (`CODEX_HOME` moves it). It lives in the agent's own folder, so it is still there when the agent's MCP server has failed, which is when the agent's Tricot tools are not. The skill never changes the agent's permissions or its settings. Some agents read another agent's skills folder (OMP, OpenCode, Goose and Cursor read `~/.claude/skills`, and OMP and Cursor `~/.codex/skills`), so they see this skill too: it tells an agent that isn't the one it was written for to give its own name or id to `--agent`, so the page is made as that agent and what you ask on it comes to that agent.

- **When the agent uses it:** its description says so. It names the phrasings above, and that it works while Tricot is stopped or the agent's Tricot tools are missing. It says it is not for questions or edits about Tricot's own code ("show me the tests in tricot", "how does the tricot listener work") nor for what is already on the board, which Tricot's own tools handle. The body repeats the prompt hook's rules for a false alarm: a message that only mentions Tricot, a request for steps ("show me how to ..."), Tricot as a name or a path, and "in tricot" meaning the project.
- **What it teaches:** the whole of [`tricot show`](#showing-something-from-an-agents-terminal) with no need for the agent's own board connection: make the page from files or from stdin, with `--title`, `--agent <the agent's id>` and `--asked` (the person's own words); ask which board when `tricot show` lists them (exit code 2) and never choose one; hand back the link; listen for what the person asks on the page with `tricot show --listen` and answer with `--reply`. Where the agent's background command starts its next turn when it ends (Claude Code), it runs the listener there; where it doesn't (Codex), it runs the listener when the person says they have asked. If the agent has its Tricot tools, it may use them instead.
- **Bringing its tools back:** the skill's last step names the agent's own way to reconnect its Tricot tools, as a closing note and not a condition: `/mcp`, then Reconnect on `tricot`, in Claude Code; a new Codex session in Codex (`codex resume` goes on with the conversation), which has no command that brings a server back into a running session.
- **A Tricot with no `tricot show`:** Homebrew's 0.1.6 answers "Unknown command". The skill then says to run `tricot update`, which may ask the person to allow it in their browser or print a command for them to run, and to ask before running that command. If it can't update, the agent asks the person to start Tricot, reconnect its tools, and ask again. It never prints the answer in the terminal instead.
- **The prompt hook stays:** it still adds its line to a message that asks to see something on Tricot, with the check that Tricot is running ([Live steps](#live-steps)). The skill does not replace it, and `tricot connect` leaves its line as it is.

The file ends with a line that says Tricot wrote it and a checksum of the text above it. A file whose checksum holds is Tricot's, as it wrote it: a Tricot that has a newer skill replaces it, after keeping a copy beside it, ending in `.tricot-backup`, readable by you alone. A file you edited, or wrote yourself under that name, is left as it is, byte for byte, with no copy, and the result says so; to have Tricot's there, move it away and run `tricot skill on`. A link is never written through or replaced (a dotfiles folder's, for the skill's folder or its file), and neither is a folder where the file goes: the result says so, and the exit code is 1.

`tricot skill [status|on|off]` is for the skill what `tricot steps [status|on|off]` is for live steps. `status`, the default, says for each agent that has skills whether it is on, off, older (a Tricot before this one wrote it: `on` brings it up to date), edited, or can't be told, and where its file is. `on` shows the exact file, asks, and writes it (`--yes` skips the question); `off` shows what it would delete (the file, the copy Tricot kept, and the skill's folder when that leaves it empty), asks, and deletes it, and a file that isn't Tricot's is left, with the way to delete it yourself. `--agent <id>` is for one agent (`claude` or `codex`); without it, every agent of them found on this computer. Each keeps its answer for `tricot connect`: `on` is a yes, `off` a no, so a skill taken out is not offered again. Without a terminal and without `--yes`, nothing is changed. Gemini CLI, Pi, OMP, OpenCode, Goose, Hermes Agent, Grok Build, Copilot CLI and Cursor have skills too, and `tricot connect` says they have none to add yet: each joins by a `skill` line in its server half, naming its skills folder and its way to reconnect its tools.

## Live steps

The first `tricot` in a terminal finds the agents on your machine (Claude Code, Codex, Pi, OMP, Gemini CLI, OpenCode, Goose, Hermes Agent, Grok Build, Copilot CLI) and asks once whether to show their steps live on your boards ("Reading src/app.ts", "Running npm test" on the board). It lists the files it would write for each agent; a yes adds a small hook to each agent's own settings, for every project, and a no is remembered too (in the data folder), so it isn't asked again. `tricot connect` asks the same for every agent that has live steps, in its own question ([above](#connecting-an-agent)), and keeps each agent's answer in the same file: the first `tricot` then asks only about an agent `tricot connect` didn't answer for, such as one installed after it ran. It never asks without a terminal, in CI, or with `--no-ask`; `--verbose` shows every line first. `tricot steps` shows where each agent stands, and `tricot steps on|off [--agent claude|codex|pi|omp|gemini|opencode|goose|hermes|grok|copilot]` turns them on or off later, again showing the lines and asking first (`--yes` skips the question). Each agent's panel in Tricot has the same as a "Live steps" switch, which shows the exact files and lines before it writes anything; agents can't turn it on or off themselves. Codex runs a new hook only once you trust it in its `/hooks`, which Tricot says when it sets it up; Hermes Agent asks you to approve each hook the first time it runs it (`hermes hooks list` shows which are approved). Goose's steps are a plugin of its own, `~/.agents/plugins/tricot-steps/`, whose hooks Goose runs with `sh` (on Windows, from the bash that comes with Git for Windows). Copilot CLI's are a hook file of their own, `~/.copilot/hooks/tricot-steps.json`; Copilot refuses a tool when a hook before it can't run at all, so its steps need `node` on the PATH Copilot runs with. Hermes keeps its hooks in `config.yaml`, which Tricot doesn't parse: it adds one `hooks:` section between two comment lines, changes nothing else in the file, and stops, saying so, when the file already has a `hooks:` section of its own or isn't there yet (Hermes makes it the first time it runs). None of this touches a project's own settings: a project that still has its own hook, from `tricot steps on --agent claude --project`, keeps it, and each step still shows once (the board keeps one of the two copies).

Live steps also pass on each agent's usage, for the Usage section of its panel, and only as numbers. Claude Code tells its plan usage only to its status line, so turning Claude's live steps on also sets `statusLine` in `~/.claude/settings.json` to Tricot's `tricot-usage.mjs`: it keeps from Claude Code's status-line input only the 5-hour and weekly windows (how much is used, when each resets), the session's cost and how full its context is, sends those to Tricot, then runs your own status line with the same input and prints what it prints. Your own status line is kept in `~/.claude/hooks/tricot-usage.json`, and turning live steps off puts it back exactly (or none, if you had none). If you set a status line yourself later (`/statusline`), Tricot leaves it alone and the panel says plan usage stopped. Codex's hook, at the end of each turn, reads the last 256 KB of Codex's own session file and sends only its plan windows, plan and token totals. Pi, OMP and OpenCode send their session's tokens and cost at the end of each turn; Gemini CLI, Goose, Hermes Agent, Grok Build and Copilot CLI share nothing Tricot can reach. Nothing reads a login or asks a usage API, and Tricot keeps the numbers in memory only. To stop it, turn live steps off for that agent (`tricot steps off --agent claude`, or the switch in its panel).

With live steps on, Claude Code's and Codex's permission prompts come to the board too: when one asks to run something, its request waits on the board, as a toast wherever you are in Tricot, and on the chat bar, with Allow, Allow for this session (Claude Code only) and Deny, where you can say why for the agent to read. Allow for this session also allows what Claude Code suggested with the request, for the rest of the session, and Tricot lists each rule, mode and folder that adds; it is offered only when it can list all of them in full. What it asks to run shows exactly as it sent it. When Claude Code asks you a question with its own question tool (`AskUserQuestion`), the request shows as the question: each of its questions with its options as radio buttons, or checkboxes when you may pick several, and an Other choice for your own words. Send answer hands your picks back as the tool's answers, so Claude Code goes on with them; Answer in the terminal leaves the question to the terminal, which asks as usual. Codex's hooks can't answer a question, so its questions are asked in the terminal. A background tab says so in its title ("⏸ Claude needs you"), with a system notification if you turned them on. A small hook, `tricot-approve.mjs`, beside the steps hook, sends the request to Tricot and waits for your answer, for as long as you take; it never answers on its own, and when Tricot isn't running (it tries once more, so the terminal asks within a second) or anything goes wrong, the agent asks in the terminal as usual. It believes only the Tricot that holds your data folder (`~/.tricot`, or `TRICOT_DATA_DIR` in the agent's environment): each start of Tricot writes a random secret in its `server.lock`, which only your account can read, and the hook sends a fresh random challenge with everything it asks and prints an answer only when the board proves it holds that secret (an HMAC of the challenge, the request and the answer). Another program that takes the port while Tricot restarts has no secret, so it gets no answer through and never sees what the agent asked to run; a Tricot from before this check, which writes no secret, and a board on another computer, where the hook has no lock to read, make the terminal ask. It works the same on Windows, which has no `lsof`. A program running as you can read the secret too, so this stops a stand-in server, not a determined one. If the agent stops waiting (the prompt answered in the terminal, or the session ended), the request leaves the board. Only a person answers, from a browser or Tricot terminal they let in, on this computer: no MCP tool can, and a page that isn't let in sees who waits, not what they ask. Turning live steps off takes the approval hook out with the rest.

With live steps on, a message you type straight into Claude Code, Codex, Gemini CLI, Hermes Agent, Pi or OMP that opens with `^` and a lens's name (`^Design please review this`, `^legal: is this licence ok?`, in any case) is answered through that lens, as a message sent with a lens from the board is. A small hook, `tricot-prompt.mjs`, beside the steps hook, runs on each prompt before the model reads it (`UserPromptSubmit` in Claude Code and Codex, `BeforeAgent` in Gemini CLI, where it is named `tricot-lens`, `pre_llm_call` in Hermes) and adds the lens's brief beside your message: "Answer this message through the Design lens: …". In Pi and OMP, Tricot's steps extension does the same on `before_agent_start`, as a message of its own beside yours that the model reads and the terminal doesn't show; that, and the line below, is all the extension changes. Neither changes what you typed, so `^Design` stays in the message. They know Tricot's own lenses, Legal, Design, Performance, Security, Architect and Marketing, from `tricot-lenses.mjs` beside them (the same list the board offers); `^General` adds nothing, and any other name adds nothing either, the agent showing you a line that says so (Hermes has no such line). They read your prompt where it is, send none of your words anywhere and work with Tricot closed; on any error, or after a second, the prompt goes through as typed (Hermes, Pi and OMP read a failed hook or handler as nothing to add). Codex runs the hook once you trust it in its `/hooks`, and Hermes once you approve it, as each does the steps hook. In Pi, a message sent while it is still working (a steer or a follow-up) goes as typed. `tricot claude` gives its session the same hook without changing your settings. Turning live steps off takes it out with the rest. Other agents get `^Design` as you typed it, with nothing added: OpenCode 2's prompt hook refuses the prompt when the hook fails, and Copilot CLI's hooks reference says it drops what a command hook prints for a prompt.

**What an agent is working on.** The hook also sends the agent's to-do list as it writes it (Claude Code's TodoWrite or its tasks, Codex's plan, Gemini CLI's and OpenCode's to-do lists: each item's words and whether it is done, being done or next) and the names of the files a step changes. Click the line under a message an agent is working on, or the pill of a thread an agent owns over the chat bar, and Tricot shows the peek: the agent's plan with how far along it is, what it and its helpers are doing now (or its last steps), and the files it changed this turn. It is kept in memory, like the steps, for two hours after the agent's last step, and never in a board. Live steps set up before this don't send the list until you run `tricot steps on` again.

The same hook, and Pi's and OMP's extension, also reads your message for a request to see something on Tricot, its board or its canvas ("show me the last dev log in tricot", "can you put the auth flow on the board", "draw the architecture on the canvas"), and adds a line for the agent beside it: you likely want this shown on Tricot, so make a Sketchbook page showing it and answer with its link, or run `tricot show` without its Tricot tools ([above](#showing-something-from-an-agents-terminal)); with `^Design` as well, it gets both. It goes by your words alone, from `tricot-show.mjs` beside the hook: a request to show (show, draw, sketch, diagram, map out, lay out, visualise, display, put; "let me see", "can I see"; "make a diagram"), said as a request, not a question about what something shows ("does Tricot show…") nor a request for steps ("show me how to…"), and aimed later in the same sentence at Tricot as a place: on, onto, in or into Tricot, the Tricot board, the board, the canvas or the Sketchbook. A message that only mentions Tricot gets nothing, nor does one where Tricot is part of a path or a name (`tricot/src`, `src/tricot`, `tricot.ts`, tricot's listener) or comes before a word for code (the tricot repo, the canvas element), one about what is already on the board, or what is in a code block. In a project named tricot, "in tricot" can mean the project, so it counts only when what you ask to see names no code (no file, folder, path, test, function or commit), when it ends what you ask or comes straight after the verb, and never after *put*: "show me the last dev log in tricot" gets the line, "show me the tests in tricot", "show me how the dev log in tricot works" and "put a check in tricot" don't. The line says it is a guess, and tells the agent to go by your words when you meant something else. Before it adds the line, the hook asks the board whether it is running, at the address `tricot steps on` gave it: a request that carries none of your words, made only for such a message. With Tricot stopped, the agent's Tricot tools are gone (its MCP server has failed), so the line says that Tricot isn't running instead, and that you start it and then run `/mcp` so the tools reconnect. When the `tricot` on your PATH has the `tricot show` command (`tricot show --help` answers), the line names it as the agent's own way, which starts Tricot; when it hasn't, as with Homebrew's 0.1.6, it doesn't. A board that is up, or too slow to tell, gets the line as above. All of this takes under a second, and only a message that asks to see something on Tricot waits for it. Live steps set up before this check came don't have it until you run `tricot steps on` again, which replaces the hook's files and its command, now carrying the board's address. The [Tricot skill](#the-tricot-skill) does the same job from the agent's own folder, and works with Tricot stopped and with no hook; the hook's line stays for live steps.

`tricot steps on --agent claude --project`, run in a project, offers to add a Claude Code hook to its `.claude/settings.json` (it shows the JSON and asks first): the board then shows what Claude is doing, one line per step ("Running npm test"), and a command or subagent that takes a while stays live until it ends ("Ran npm test (42 s)"). The same line shows under a message you're waiting on Claude to answer, and on the project's row on the home page. The hook sends no file contents or command output, runs in the background and does nothing when Tricot isn't running. With `--narration` it also sends the first line of each message Claude writes in the terminal (never its thinking); that is off unless you ask for it. `tricot steps off --agent claude --project` takes it out again.

## Updating and removing it

The same `npm install -g tricot` updates it (`brew upgrade tricotstudio/tap/tricot` with Homebrew), and `npm uninstall -g tricot` removes the command; your boards stay in `~/.tricot` either way. To try it once without installing, `npx tricot` runs the same command.

Two installs can exist at once, say an old `npm install -g tricot` under nvm and Homebrew's, and the first `tricot` on your `PATH` is the one that runs, whichever is newer. `which -a tricot` (`where tricot` on Windows) lists them: remove the one you don't want, with `npm uninstall -g tricot` or `brew uninstall tricotstudio/tap/tricot`. `tricot --version` is the version of the command you ran, so `tricot update` says when it is older than the running board ("This command is 0.1.1 but the board runs 0.1.4."), lists each `tricot` on your `PATH` and the command to remove the old one; it never removes anything itself.

The commands that reach a running board (`tricot listen`, `tricot show`, `tricot claude` and the other agent commands) read its version first, and stop with a plain sentence naming `tricot update` when the board is too old for the command, or the command too old for the board; a board older than the command that the command can still use is said in a line. A command or option `tricot` doesn't know says the same when the board it was meant for is newer. The `tricot listen` a board hands an agent runs as the board's own version (its Node and its script), so an older `tricot` on the agent's `PATH` doesn't matter.
