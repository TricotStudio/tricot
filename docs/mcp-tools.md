# MCP tools

Back to the [README](../README.md).

| Tool | Purpose |
| --- | --- |
| `list_boards`, `create_board`, `get_board` | Find or start a board; `get_board` returns its Sketchbook pages, requests, threads and people, plus a cursor. |
| `search` | Search a board, or every board, for past and current work (comments and canvas blocks) before making something, so nothing already worked out is made again. |
| `comment` | Reply in the comment thread (`pin_id`) on a pinned part of a Sketchbook page. An @-mention of another agent hands it a question or a piece of work, as a person's would; after four agent-to-agent mentions in a row with no person in between, further ones there wait for a person (threads too). |
| `react` | 👍, 👎 or 👀 on a comment or thread message (the latest by someone else, or by its id). People's reactions to the agent's own comments come through its updates. |
| `get_thread`, `reply_in_thread`, `start_thread` | Threads are conversations through which people work on the project with agents, each through a lens (General, Legal, Design…). A person's message can ask for another lens on itself alone (`^Design` in the chat bar): the agent's updates and `get_thread` say *For this message, answer through its Design lens…*, in place of the thread's, and the next message goes back to the thread's. `read_guide("conversation")` lists the lenses and their briefs, for an agent that gets a `^Name` as plain text. Read one in full, answer in it (`then_wait` keeps listening in the same call), or open one to raise a risk or a question. A thread a person started over blocks they selected on a Sketchbook page (its note names the blocks, and `get_board` lists it as started over the page with N blocks selected) is for talking them through: the agent answers in plain words with its reasons, and makes blocks only once the person asks or agrees, straight away when they say what to make. What it adds with the thread's id (`add_block` with `page_id`) is shown in a group beside the blocks, made then (`add_block` puts its block in that group unless one is named); the tool's result says so. `get_canvas` heads that group with the thread it shows. A thread a person started in Files about the file they had open (its note names the file and its block, and `get_board` lists it as started in Files about that file) is for talking that file through: the agent reads the file itself in its repository, answers in plain words, and changes the file only once the person asks for a change or agrees to its suggestion. |
| `read_guide` | How to use the tools well, by topic (canvas, blocks, conversation): the advice each tool's description leaves out, read when the agent first does that kind of work. Read-only. |
| `report_skills` | Tell Tricot which skills the agent has, so people can call them with "/" from a comment or a thread message. |
| `get_updates`, `wait_for_updates` | Activity since a cursor from anyone else; the second blocks until something concerns the agent (`src/core/concerns.ts`: a message, mention or request for it or any agent, a person pairing with it, or a reply from whoever it @-mentioned), and brings what else happened meanwhile with it, for up to 15 minutes per call (4½ for Claude Code, which cuts a call silent for 5 minutes and, after the computer slept, one whose progress was paused with it, and less for any client that cuts long calls sooner: its registry entry says), sending progress while it waits. In a session Tricot's terminal started and wakes (its MCP address names that terminal, `wake=<its word>`, and that terminal holds it), the wait doesn't wait: it returns the updates at once and tells the agent to end its turn, as the terminal types a line in its prompt when something concerns it. It waits after all, and says why, when no terminal holds the agent on that board, or when the session calls it again at once with nothing new. An agent connected on its own whose client starts a turn when a command it runs in the background ends (the registry's `mcpClient.listens`: Claude Code 2.1.288 or later), from this computer to a board that listens on it alone, doesn't wait either: the wait returns at once with `tricot listen --board=<id> --session=<word> --url=<address>` for it to run in the background before it ends its turn, its session's word in it (each value in one word with its option, so a word that starts with `-` is read as a value). The command is the board's own `tricot` (its Node and its script, quoted for bash or zsh), so it runs as the board's version whatever `tricot` the agent's `PATH` finds; a board that doesn't know how it was started, or whose install has gone, gives plain `tricot listen` and says what to do if that one is too old (`src/server/mcp/session.ts` `listenCommand`). The command holds the agent asleep, and ends, starting its next turn, when something concerns it (`src/server/listeners.ts`). The agent's instructions and this tool's description say so, from the name and version its client gives. A message that tags the agent with a model and thinking level (`@Claude:opus:high`) adds "asks you to do this on opus at high thinking: hand the work to a subagent on that model and thinking level, and keep your own session as it is", for an agent that can (Claude Code); another gets the message as it would without the tag. A Codex connected on its own, 0.166 or later, whose calls carry its thread id, is woken through Codex itself instead: its waits end its turn, and Tricot runs `codex queue --thread <id>` with one fixed line when something concerns it (`src/server/codexWake.ts`). |
| `set_project_folder` | Set a board’s project folder to an existing directory inside home, or clear it with `null`. `create_board` also accepts `folder`; `get_board` names it. |
| `take_request`, `finish_request` | Take a person's request about blocks they selected on a Sketchbook page, asked before a message sent with blocks selected began a thread (now it is a thread, answered with `reply_in_thread`), answer it with blocks in the group made for it, then mark it done with a note that says what the agent made and why. |
| `get_canvas`, `get_block` | Read a canvas in reading order, by group, with links and images attached; or one block in full. A canvas is a page of the Sketchbook (`page_id`, required); `add_block`, `add_group` and the other canvas tools take the same. |
| `add_page`, `update_page` | Add a page to the board's Sketchbook, a canvas of its own for an idea being explored, or rename one; `get_board` lists the pages with their ids. Each answers with the page's link, to give the person. When a person asks an agent to see something on or in Tricot, the board or the canvas ("show me how signup works on Tricot", "show me the last dev log in tricot", "draw the auth flow on the board"), it makes a page showing it, passes `asked` (their words), and answers with that link; with [live steps](../cli.md#live-steps) on, the prompt hook adds a line saying so beside such a message. A page an agent makes is that agent's: what people ask on it goes to it unless they @-mention another, and when the agent isn't listening on the board, `add_page` tells it to. Only people arrange pages and delete them. |
| `add_block`, `update_block` | Add a note (task lists included), table, diagram, image, link, diff, code, chart, 3D scene, website or shape (a rectangle, ellipse, diamond, text label or free arrow, with a colour, a line's weight and bold words, and an arrow its `ends`; arrows between blocks are `link`s) (auto-placed, optionally in a group); edit it in place. A diff can name a git repository on this computer instead of sending the patch (`repo`, with `range`, `against` or `paths`), and a code block a file (`file`, with `lines`): Tricot reads them, inside the home folder only. `update_block` takes the `rev` the agent last read and is refused, with the current content, if someone changed the block since. |
| `add_group`, `link`, `remove_item` | Name a group, draw a labelled link, remove a block, group, link or pin. |
| `restore_item` | Put back a block, group, link or pin removed in the last 30 days, as it was and with the same id; a thread a person deleted comes back with its messages. |

Tricot Canvas lists these 26 tools, and offers the guide topics `canvas`, `blocks` and `conversation`. `test/mcpTools.test.ts` holds this table to the tools a server lists, and each tool's description to the guide topic it points to.

A session with a role (`src/core/roles.ts`, named on its MCP address: `role=coordinator`, or `role=orchestrator` with `thread=<id>`) lists one tool more, offers its guide topic, and is told its role in a line ahead of the rest. A session with none lists and is told exactly what it was:

| Tool | Purpose |
| --- | --- |
| `route_to_thread` | The coordinator's (`tricot claude --coordinate`, `read_guide("coordinating")`). It answers people in the chat bar, whose threads are its while it is on the board, and does no work itself: it sends a person's message on to the thread its work belongs to (`to_thread_id`), whose owner hears it at once, or starts a thread for new work (`title`, `brief`, `agent`) that an orchestrator owns, which Tricot's terminal starts in a tab of its own. Where it was asked, it says where it went, and the page takes the person there. |
| `set_thread_status` | The orchestrator's, for the thread it owns (`read_guide("orchestrating")`): working, needs-you while it waits on a person, or done, with a summary posted first. A person's message there sets it back to working; done tells the coordinator, which tells the person. |

Connected services add tools of their own, once a person has connected them on the Connectors page. They read what people link on a canvas, and none of them acts as a person in the service:

| Tool | Purpose |
| --- | --- |
| `read_google_doc`, `edit_google_doc` | Read the Google Doc a link block points to, with the draft of edits made in Tricot; change that draft. Nothing reaches Google until a person saves it. |
| `read_figma_frame` | Read a Figma frame (as a picture) and its comments, by a link block or an address. Read-only. |
| `read_github` | Read a GitHub pull request, issue or file by its link: state, checks, changed files, the diff on request. Read-only. |
| `read_slack` | Read a Slack message or thread by its link: who wrote each message, when, and what they said. Read-only: there is no tool that posts to Slack, because that would act as a person. |
| `read_linear_issue`, `search_linear_issues` | Read a Linear issue by its linear.app link or identifier (`ENG-123`): status, assignee, priority, labels, description; or search issues by words. Read-only: nothing is written back to Linear. |

The server also sends MCP `instructions` describing this protocol, which clients show to the agent automatically. Each tool's description says what it does and what to pass, and stays short, since every session carries them all; how to use the tools well is in `read_guide`. Writes that are hard to read come back with advice; advice never rejects a write.
